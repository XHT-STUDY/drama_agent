## 第一部分：项目定位与架构（Q01-Q09）

### Q01. 请用两分钟介绍 DramaAgent，你解决了什么问题？

**可直接回答：**我做的 DramaAgent 是面向中文短剧创作的 Agent 应用。短剧不是一次生成一篇文本就结束，作者会先确认设定和大纲，再分批写剧本、评估、修改和导出。难点是多轮修改后仍要知道当前是哪一稿、角色已经知道什么，以及中途失败后从哪里继续。我把自然语言请求先转成受限计划，写操作由用户确认；执行层用 LangGraph 跑长任务，正文与评估以不可变 Artifact 留存，并用结构化记忆和版本快照支撑后续操作。现在能证明的是链路、恢复和离线评测按既定口径工作；真实用户的创作效率与成稿质量，还需要单独验证。 [P1] [P6]

### Q02. 它是 Agent 还是固定 Workflow？

**可直接回答：**我会把它称为“受约束的 Agent 加确定性工作流”。用户说“修改第三集”“解释这次评分”，系统需要结合当前作品状态判断意图、目标和下一步动作，这部分有模型参与；真正写剧本、评分、修订的执行顺序，以及权限、版本、预算和终态判断，则由固定工作流与服务端规则控制。如果把 Agent 定义为模型能自由发现并调用任意工具，那这个项目并不属于那一类。我选择这个边界，是因为创作写操作有持久副作用，先把可控性做好更符合场景。 [P1] [O1]

### Q03. 为什么选 Plan-and-Execute，而不是自由 ReAct 或多 Agent？

**可直接回答：**我选 Plan-and-Execute，是因为一个剧本任务会跨多集、跨多次确认，还可能中断后续跑。先让模型提出受限计划，再把影响范围和目标稿展示给用户确认，执行阶段由固定图推进，比较容易处理过期计划、预算和失败恢复。自由 ReAct 适合需要边观察边探索的任务，但这里多数动作和阶段已知，开放工具循环会增加费用和误写风险。多 Agent 也不是天然更强，除非把并行收益、沟通开销和错误传播放在同一套评测中证明有增益，否则我不会只为了架构名称增加角色。 [P1] [O1]

### Q04. 说出一条请求从输入到结果的完整控制链。

**可直接回答：**一条写操作从用户输入开始：系统先持久化 AgentTurn，作为这次输入和重试的收据；确定性预检拦截明显的越界或冲突，再由 Planner 产出受限意图、目标和约束。服务端解析真实目标 Artifact，保存待确认的 AgentAction 和源稿快照。用户确认时重新校验版本和权限，随后创建 WorkflowRun。Dispatcher 领取 Run，LangGraph 按节点执行，阶段产物落到 PostgreSQL 的 Artifact，事件经数据库和 SSE 送到前端。最后 Outcome 根据 Run 与产物证据判断是否达成，不把模型自己说“完成了”当最终结果。只读解释请求则不创建 Run。 [P1]

### Q05. Turn、Action、Run、Artifact 分别解决什么问题？

**可直接回答：**我把四层实体分开，是为了让每个状态都有明确含义。Turn 表示“用户这次到底说了什么”，负责输入幂等；Action 表示“系统打算做什么、等待谁确认”，负责计划和权限；Run 表示“这件事实际执行到哪一步”，负责租约、恢复和终态；Artifact 是已经生成的作品、评估或修订版本，属于业务事实。如果都放进聊天消息表，双击确认、任务崩溃和多稿并存时就无法可靠回答哪个动作执行过、哪个版本被引用，也很难审计。 [P1]

### Q06. 为什么要把 LLM 调用放在数据库事务外？

**可直接回答：**LLM 调用的耗时和失败都不可控，我不会在数据库事务里等它返回。项目把输入收据和租约创建放在短事务里，事务结束后调用模型，拿到结果再开短事务保存计划。这样数据库连接和行锁不会跟着模型请求占用几十秒。中间会有状态变化，所以第二个事务必须重新检查租约所有权、项目版本和目标是否仍有效。这个设计不是消除竞态，而是把竞态显式地交给版本与约束处理。 [P1]

### Q07. 项目为什么将 PostgreSQL 设为事实源、Redis 设为加速层？

**可直接回答：**PostgreSQL 保存消息、Run、Artifact 和可重放事件，因为它们需要持久化、约束并发并能追溯。Redis 只承担最近消息窗口和事件通知：它能降低读取和推送延迟，但丢了缓存仍可从 PostgreSQL 重新取消息；Pub/Sub 漏了通知，也能通过数据库事件补进度。这使事实源只有一处。代价是回源和 SSE 轮询会增加数据库压力，所以流量增大后要监控事件表与查询负载，不能把 Redis 当成可靠消息队列来承诺送达。 [P1]

### Q08. 为什么 Artifact 不可变？版本和来源关系有什么用？

**可直接回答：**剧本后续会被评分、修订、导出和回看，覆盖旧稿会让这些操作失去依据。我让每次写入形成新的 Artifact，保存版本、checksum、输入哈希及来源关系；评估必须指向当时评的那份剧本，导出也基于确定版本。这样用户能比较稿件，系统能在确认 Action 时发现源稿已经变化，重试时也能识别同一输入。这里还有一个业务边界：生成了候选稿，不等于作者已经采纳它，所以“当前有效稿”和“历史候选稿”也要分清。 [P1] [P10]

### Q09. 这个项目最大的技术取舍是什么？

**可直接回答：**我最核心的取舍，是只让模型决定它擅长的部分，例如理解用户意图和生成内容；权限、目标归属、版本、预算和结果判定交给服务端。这让系统的写操作有可解释的路径，也能做确定性测试和故障恢复。代价是新动作需要扩白名单、状态机和评测，单项目活动 Run 也被限制为一个，吞吐不是最大化的。但在需要反复确认、修改和追责的创作场景，我认为先保证不写错稿，比追求完全自由的工具调用更重要。 [P1]

## 第二部分：规划、工具与 MCP（Q10-Q20）

### Q10. 模型识别错意图会造成什么后果，如何降低风险？

**可直接回答：**意图识别错在“解释评分”上，主要损失是用户体验；错在“修改第三集”上，可能直接写错作品版本。因此我把风险分层：明显越界、冲突、目标不清的请求先由确定性 preflight 拦截；Planner 只能输出白名单意图和目标选择器；服务端再按当前项目状态解析真实 Artifact，写操作还要用户确认。评测也按业务损失拆开看，不只看一个 intent F1，而要重点看“本应澄清却执行”和目标集数错误。项目新版评测集已经覆盖这些合同，但真实模型联合指标尚未跑完。 [P1] [P3]

### Q11. Planner 输出为什么不能包含任意工具名、Artifact ID 或 SQL？

**可直接回答：**Planner 的输出只能是建议，不能是授权。即便模型返回一个看起来合法的 Artifact ID 或 SQL，它也可能来自错误上下文或被检索文本诱导；让模型直接指定这些值，会绕过项目归属和权限。我的做法是让它输出受限的意图、目标类型、集数和约束，再由服务端在当前项目内解析 ID、校验版本、Schema、权限与预算。Function Calling 或 JSON Schema 可以改善输出结构，不能代替业务授权，这个边界是写操作安全的关键。 [P1] [O4]

### Q12. 什么时候该澄清，什么时候该使用默认值？

**可直接回答：**我会按“猜错的代价”决定是否澄清。像“我想写一个逆袭故事”，系统有默认分阶段流程和默认集数，可以先给计划，不必追问用户选哪种流程；但“把它改一下”没有明确当前稿，或者集数越界、约束互相冲突，就应该先问清楚。早期 Planner 曾把愿望式创作请求连续澄清两次，用户实测暴露了入口断裂；后来我们调整默认语义并补回归用例。目标不是一味少问，而是让必要澄清召回和过度澄清率同时可测。 [P3] [P11]

### Q13. 计划确认后用户又改了剧本，旧计划怎么办？

**可直接回答：**计划生成时看到的作品状态只是快照。Action 会记录源 Artifact 的 ID、版本和 checksum；用户点确认时，我会在数据库行锁内重新读取当前有效稿。如果作者在这期间改了剧本，旧计划就标记为 stale，需要基于新稿重新规划。仅靠前端把按钮置灰不够，因为用户可能开多个标签页，页面也可能很久没刷新；客户端传回的旧计划本身也不能被信任。 [P1]

### Q14. 如何保证双击确认或请求重试不会执行两次？

**可直接回答：**我把幂等分成三层。输入层的 Turn 用幂等键避免同一请求被重复接收；确认层锁住 Action，已确认的请求返回原有 Run；执行层 Run 用幂等键、请求哈希和数据库单活动 Run 约束，避免并发启动两份写任务。如果同一个键携带不同参数，应返回冲突而不是悄悄复用。分批续跑还要校验 stage_generation，否则上一批的“继续”请求可能被重放到下一批。这保证的是业务副作用尽量只落一次，不代表外部模型 API 绝对只收费一次。 [P1] [P2]

### Q15. Function Calling、Tool Use、MCP 三者怎样区分？

**可直接回答：**Function Calling 或 Tool Use 指的是模型按约定结构表达“想调用哪个工具、带什么参数”；真正执行工具的仍是应用。MCP 则是客户端和工具服务之间统一发现、描述与调用 tools、resources、prompts 的协议。我在这个项目里做的是默认关闭的 MCP 消费侧适配骨架，服务端仍要校验工具能力、参数和结果；项目没有对外提供 MCP Server，也没有让模型跳过 Action 确认门直接调用写工具。面试时我会把“协议接入”和“业务已经安全可用”分开说。 [P1] [P12] [O7]

### Q16. Tool、Skill、Workflow 的边界是什么？

**可直接回答：**我的划分标准是可确定性和副作用。Tool 负责可以明确计算或执行的动作，比如 Diff、结构特征计算和导出；Skill 封装一次有领域输入输出的模型能力，比如 Planner、Writer、Evaluator；Workflow 决定这些能力按什么状态和条件运行。字数统计若交给模型会增加成本且不稳定，长篇创作若硬编码成普通函数又缺少表达能力。拆开之后，各层的失败和测试边界更清楚：Tool 测确定结果，Skill 测输出契约，Workflow 测状态推进。 [P1]

### Q17. Tool 返回的内容可能包含 Prompt 注入，怎么处理？

**可直接回答：**我默认工具结果和检索片段都是不可信数据，即使它们写着“忽略之前指令”，也不能升级为系统指令。服务端先限制工具能读写的项目范围、输出大小和调用预算；模型给出的下一步动作必须再次通过白名单、权限和版本检查。项目有模板中的内容边界和 Action 确认门，但提示词分隔只是软防线，不能宣称完全防住 Prompt 注入。外部工具异常也应返回可诊断的通用错误，不把密钥或连接信息带进模型上下文。 [P7] [P12] [O8]

### Q18. 如何设计一个安全的写工具？

**可直接回答：**我会先给写工具定义严格的输入输出 Schema、权限范围、幂等键、目标版本和预期副作用。执行前由服务端验证项目归属与源稿新鲜度，必要时给用户展示 dry run 或 Diff 并确认；执行后记录生成物、来源和审计事件。即使工具由 MCP 暴露，工具声明也只负责描述能力，客户端仍要验证参数和响应。对可能造成大面积修改的动作，失败补偿和回滚方式要在设计时确定，而不是等模型调用失败后再想办法。 [P1] [O7]

### Q19. 多 Agent 比单 Agent 一定更好吗？

**可直接回答：**不一定。多 Agent 适合能并行分解、角色有独立工具或信息、合并结果可验证的任务；否则它会引入更多上下文同步、冲突裁决、延迟和 token 成本。我会先做单 Agent 或固定 Workflow 基线，再在同一批任务上比较成功率、耗时、花费和错误传播，证明增益后才引入。DramaAgent 目前是单编排器加专业 Skill，没有多 Agent 协作的真实实验，因此我会讲清选型依据，而不会把它包装成已落地的多智能体系统。 [P1] [O1]

### Q20. 面试官要求当场为项目加一个「联网查题材热度」工具，你怎么设计？

**可直接回答：**我会先把“题材热度”定义为只读辅助信息，确定可信数据源、更新时间、查询频率和引用格式，而不是让工具直接改 Story Bible。Planner 可以建议什么时候查，服务端负责调用预算、超时、项目绑定和返回内容的低权威标记；若外部服务失败，创作应能退化到现有资料，并明确告诉用户没有实时热度依据。上线前我会用固定题材集检查来源正确率、过期数据比例和对创作建议的影响。尤其不能把热度推测说成已验证的市场事实。 [P1] [P7] [O7]

## 第三部分：LangGraph、长任务与一致性（Q21-Q31）

### Q21. 为什么用 LangGraph？状态里存什么？

**可直接回答：**我用 LangGraph 是因为创作不是一次同步调用：Story Bible、大纲、分批剧本、评估和修订会按状态分支，也会在人工确认处暂停。图能清楚表示节点、条件和续跑位置，但我没有把整部剧本都塞进图状态；Checkpoint 主要保存 Artifact ID、已完成节点和门状态，大文本仍在 PostgreSQL。这样恢复时能从确定的业务产物继续，也避免每次 checkpoint 复制大段正文。框架提供执行机制，Action、Run、版本和权限仍由应用自己负责。 [P1] [O2]

### Q22. Checkpoint 能保证「模型只收费一次」吗？

**可直接回答：**Checkpoint 只能帮我恢复已经持久化的进度，不能保证外部模型“恰好调用一次”。最难的窗口是模型已经返回、费用已经产生，但进程在 Artifact 提交前崩溃，此时系统没有可复用的持久结果，重试可能再次付费。我的做法是逐集提交、记录 completed_nodes 和 input_hash，并用预算限制损失；已落库的 Artifact 不覆盖、不重复创建。面试里我会明确区分业务效果幂等和模型调用费用幂等，后者在普通第三方 API 条件下无法单靠本地 Checkpoint 承诺。 [P1] [P2] [O2]

### Q23. 数据库租约调度如何处理 Worker 崩溃？

**可直接回答：**Run 先以 queued 状态进入 PostgreSQL，Dispatcher 用 `FOR UPDATE SKIP LOCKED` 在并发 Worker 之间领取，写入 owner 和过期时间；运行期间续租。Worker 崩溃后租约到期，其他 Worker 可以重新接管，从 Checkpoint 和持久化 Artifact 判断已完成到哪里；重试次数耗尽则明确失败并回写 Action 状态，避免任务永远停在 running。`SKIP LOCKED` 解决的是并发领取，不负责外部副作用去重，所以每个阶段还要有业务幂等与版本校验。 [P1] [O6]

### Q24. 为什么需要数据库唯一约束，应用层先检查不够吗？

**可直接回答：**应用层“先查有没有活动 Run，再创建”存在竞态：两个请求可能同时查到没有，然后都创建成功。项目用数据库部分唯一索引约束同项目只能有一个 queued 或 running Run，作为最终兜底；应用层检查只负责给出更友好的错误。确认 Action 时还会锁定记录、检查是否已确认以及源稿快照是否过期。这样分别处理双击、并发请求和作品版本变化，而不是用一把大锁模糊所有问题。 [P1] [P2]

### Q25. 「继续写下一批」怎样避免旧确认请求重放？

**可直接回答：**同一个 Run 可能先后停在大纲确认门和多个剧本批次门，所以只传 run_id 不足以判断一次“继续”属于哪一门。我给门加 stage_generation，确认请求携带预期世代和幂等键；同键同参重试返回原结果，参数变化或门已经推进则返回冲突。这样用户网络超时后可以安全重试，旧页面或旧请求也不会把下一批剧本误推进。这里的重点是把“当前门”变成可验证的状态，而不是依赖前端按钮是否可见。 [P2] [P11]

### Q26. 自动修订如何避免无限循环？

**可直接回答：**自动修订必须有明确退出条件。我先用确定性评分规则选低分集，再限制最大修订轮次和 token 预算；每轮之后检查连续性并重新评估。如果仍未达标、分数明显下降或出现不能自动判断的冲突，就停在人工复核，而不是让模型无限自我反思。Outcome 可以提出后续 Action，但仍要用户确认。这样系统能尝试改善可验证的问题，也承认“剧本好不好看”最终需要作者判断。 [P1] [P2]

### Q27. 取消任务时，正在进行的 LLM 请求会立刻停止吗？

**可直接回答：**当前实现是协作式取消。queued Run 还没开始，系统可以直接标取消；running Run 会在节点边界检查取消标记，停止后续节点和产物提交。但若某个第三方 LLM 请求已经发出，除非 provider 和传输层支持取消，否则它通常要返回或超时，我不会说点击取消就能立刻停止计费。用户界面也应区分“已收到取消请求”和“任务已终止”，避免给出错误承诺。 [P2] [P10]

### Q28. 一集正文已保存，但剧情状态派生失败，怎么办？

**可直接回答：**我把正文保存和剧情状态派生视为两个提交点。如果本集正文已经成功落库，而角色知识、伏笔等状态派生失败，就保留正文并记录 derivation_pending_episode，之后基于确切版本重新派生。写下一集之前必须先有可信的前态；若派生仍失败，就停下来报错，不能拿旧的标题摘要冒充完整连续性状态继续写。这样既不丢用户已经得到的文本，也避免一个状态错误污染后续所有集。 [P2] [P4]

### Q29. SSE 断线或 Redis 丢消息后，前端怎样追上进度？

**可直接回答：**SSE 和 Redis Pub/Sub 负责及时通知，不负责独占事实。每个事件先持久化到 PostgreSQL，前端断线重连时带上 Last-Event-ID；服务端从该 ID 后补发数据库事件，再接实时推送。Redis 漏消息或断线时，客户端还可通过轮询已持久化进度追上。为了避免重复展示，事件要有单调 ID，前端按 ID 去重；运维上还要监控事件积压与回源查询压力。 [P1]

### Q30. 如果用户修订第 2 集，第 3 集之后的剧情状态如何处理？

**可直接回答：**修改第 2 集后，第 3 集及之后基于旧第二集推导的剧情状态不能继续当作当前事实。我会把受影响的下游状态从最早失配集标为 stale，记录它们依赖的剧本版本，再按新稿顺序重算。用户已经写出的后续正文可以保留为历史 Artifact，但系统不能无声地用旧前态生成新内容。若重算发现后续正文和新设定冲突，要给出具体来源，让作者决定改哪一稿。 [P2] [P4]

### Q31. 如果业务量增长 10 倍，这个架构会先卡在哪里？

**可直接回答：**我不会一上来就说“加更多 Worker”。先拆队列等待、模型调用、检索、数据库锁、SSE 回源和 Artifact 分页的耗时分布。这个项目单项目只允许一个活动 Run，所以同一作品的写任务天然串行；多项目并发上来后，外部模型限流和数据库连接更可能先成为瓶颈。应根据 p95、失败率和队列深度做压测，再决定是调整配额、分离 Worker、扩数据库，还是改变单项目并行语义。扩容不能破坏版本和幂等约束。 [P1] [P10]

## 第四部分：RAG 与知识库（Q32-Q43）

### Q32. 说清项目的 RAG 全链路。

**可直接回答：**RAG 链路从资料摄取开始：上传文档经格式校验和切分，调用 embedder 生成向量，连同项目、类别、版本和来源存到 PostgreSQL/pgvector。创作时按当前阶段和项目作用域过滤，再做相似度召回、去重及每文档块数限制，把命中片段和 chunk ID 记录到 ContextManifest。Story Bible、大纲、剧本写作拿到的资料类别不同，参考片段的权威始终低于用户当前指令和确切作品事实。项目有结构性链路验证，但真实 embedding provider 的质量和端到端收益还需要实测。 [P1] [P2] [P10]

### Q33. Chunk 太大或太小分别有什么问题？如何选大小？

**可直接回答：**Chunk 太小，召回的可能只是一个孤立句子，人物关系或因果条件丢了；太大，则一个块里混了多个主题，检索虽命中却占用大量上下文。我会先按标题、章节和业务语义切分，保留来源及题材、角色等元数据，再在固定查询集上比较 recall@k、MRR、证据完整性、成本和延迟。大小不是通用常数；对剧本资料，角色设定和剧情事件也不一定适合同一种切分方式。 [P1] [O10]

### Q34. Embedding 相似度高就代表内容对任务有帮助吗？

**可直接回答：**相似度高只说明向量空间里接近，不能说明这段资料有权限、够新、来源可靠，或适合当前创作阶段。项目在向量排序前先做项目和类别过滤，命中后再限制重复块和总预算；真正进入 Prompt 的片段也只是参考，不得覆盖 Story Bible 和用户明确约束。我会把检索命中与最终任务质量分开评：检索召回高却导致错误创作，说明后面的证据使用和权威控制仍有问题。 [P1] [P4] [O5]

### Q35. pgvector 里的精确检索、IVFFlat、HNSW 有何取舍？

**可直接回答：**精确检索适合作为质量基线，能知道近似索引漏掉了什么，但数据大时查询成本会上升。IVFFlat 依赖聚类，建索引前要有数据，查询速度、召回和列表参数要一起调；HNSW 是图索引，通常能取得较好的速度和召回折中，但索引内存与构建成本更高。我会先测真实资料量、过滤选择性和查询 p95，再用精确结果计算 ANN recall，不能因为用了 pgvector 就宣称已经做过 HNSW 调优。 [O5] [P1]

### Q36. 什么是混合检索和 RRF？本项目实现了吗？

**可直接回答：**混合检索通常把关键词召回和向量召回结合：BM25 对角色名、道具名、专有术语这类精确词更敏感，向量检索更擅长语义改写。RRF 不直接相加两种分数，而是根据各结果在列表中的名次融合，减少分数尺度不同带来的问题。DramaAgent 现在主要是向量检索加项目和阶段元数据过滤，尚未上线 BM25/RRF。若要加，我会先找“角色名明确却被语义结果挤掉”的坏例，再比较召回、下游质量和额外成本，证明值得增加复杂度。 [P1] [I09] [O19]

### Q37. Embedding、Reranker、LLM 生成器各做什么？

**可直接回答：**Embedding 是第一阶段的候选召回，用向量快速缩小范围；Reranker 把查询和每个候选放在一起重新打分，通常提升前几条结果的相关性；生成模型则根据最终证据完成写作或回答。它们解决的是不同问题，不能把检索后去重叫作学习型 Reranker。项目目前没有独立重排模型。我会先测 top-k 命中和引用正确率，如果候选里有正确证据但排序靠后，才优先评估重排收益，同时计算它带来的额外延迟和费用。 [P1] [I09]

### Q38. 什么是 HyDE？什么情况下不该用？

**可直接回答：**HyDE 的思路是先让生成模型写一段“假想会回答这个问题的文档”，再把这段文本向量化用于检索，适合短查询与文档表述差异较大的情况。它的风险也直接：多一次模型调用，假想内容若带着错误前提，召回会被带偏。对“查某个角色的设定”这种有明确实体的请求，我会先用原查询和元数据过滤；只有固定坏例表明语义鸿沟明显时，才做 HyDE 对照。这个方法是我的理论储备，本项目未实现。 [I09] [O18]

### Q39. 为什么不把所有知识库资料一次性塞进 Prompt？

**可直接回答：**我不会把整个知识库直接塞给模型，因为无关资料会挤占上下文，增加成本，还可能与当前设定冲突。项目按 Story Bible、大纲和写作阶段选择不同类别，限制 top-k 与每文档块数，并通过 ContextManifest 记录真正进入 Prompt 的片段。权威顺序也要固定：用户当前约束和确定版本的作品事实优先，RAG 只提供参考。若预算不足，先裁掉低价值检索片段，而不是偷偷截断当前稿件。 [P1] [P4]

### Q40. 你怎样评估 RAG，不让生成质量掩盖检索问题？

**可直接回答：**评 RAG 要先把“找没找到”与“模型用得对不对”拆开。第一层检查摄取、切分、项目隔离和固定查询的 recall@k、MRR；第二层核对最终回答或剧本引用是否来自被召回的原文；第三层再看创作约束、质量、成本和延迟。我会至少比较无 RAG、当前阶段检索和候选的混合检索，并按专有名词与长短查询分层。DramaAgent 的 FakeEmbedder E2E 证明链路接通，不代表真实语义检索已经达到某个命中率。 [P2] [P10] [O3]

### Q41. 检索失败、向量库不可用时是继续还是中断？

**可直接回答：**检索失败是否中断，取决于检索片段是不是这个任务的必需证据。若用户要求“严格依据我上传的人物资料改稿”，资料取不到就应明确失败，不能凭模型常识编造；若只是寻找题材参考，可以降级继续，但要标明本次没有使用外部资料。服务端应区分网络超时、无结果、权限过滤后无结果和向量库故障，记录到轨迹和 Manifest。这样的降级是有条件的产品决策，不是统一“失败就跳过”。 [P1] [P4]

### Q42. 用户上传的文档可能跨项目泄漏，怎么防？

**可直接回答：**跨项目泄漏是 RAG 的硬边界。上传时资料绑定 project_id 和来源版本；检索 SQL 必须先按项目权限过滤，再计算相似度，不能检索全库后在应用层删结果。生成 Prompt 前还要复核 chunk 归属，事件和引用里不能暴露其他项目的文档 ID。测试要构造两个项目里相似甚至同名的资料，验证搜索、缓存、重试和导出都不会串数据。向量接近不赋予访问权限，这一点必须在数据库查询层落实。 [P1] [P10]

### Q43. RAG 能防 Prompt 注入或幻觉吗？

**可直接回答：**RAG 能降低模型凭空编造的机会，但它不能自动防幻觉，更不能防注入。检索到的文档可能本身错误、过期，甚至写着“忽略系统要求”；模型也可能误读或过度概括。我的做法是把检索片段标为低权威数据，保留来源和版本，对可验证的引用逐条回原文检查，对权限和写操作由服务端控制。最终还要在固定坏例上测忠实度和任务结果，不能把“接了知识库”直接等同于“回答真实”。 [P7] [O8]

## 第五部分：Memory 与上下文工程（Q44-Q54）

### Q44. 对话历史、RAG 和 Memory 有什么区别？

**可直接回答：**对话历史是用户实际说过的原始消息，项目里完整保存在 PostgreSQL；短期窗口和累计摘要是从历史派生出的工作记忆，帮助模型在有限预算内保留关键约束。结构化剧情状态记录确定版本下角色知识、道具和伏笔等可演算事实；RAG 则引入外部资料。它们的来源、时效和权威都不同。我会让当前用户指令与确切作品版本优先于摘要，让摘要优先于普通参考片段，而不是把所有文字丢进向量库后统称长期记忆。 [P1] [P4]

### Q45. 为什么「只保留最近 N 条消息」会失败？

**可直接回答：**只保留最近 N 条消息会把最早、但仍有效的否决项和角色设定挤出上下文。项目的确定性对照里，旧分段摘要策略在 96 和 192 条消息时关键约束召回降到 0；累计摘要把已离开短期窗口的内容和上一版摘要一起更新，再配合最近消息。这个数字说明旧策略有明显失败模式，也说明结构化策略在离线基准上的潜力。它不是当前真实模型的用户任务完成率，所以我会同时讲实验环境和下一步要做的真实模型验证。 [P4]

### Q46. 累计摘要如何更新，怎样避免重复和覆盖？

**可直接回答：**累计摘要不能每次只总结最新一段，否则越早的约束还是会丢。我的更新方式是用上一版摘要，加上刚离开短期窗口且尚未覆盖的消息，生成第 k 版；同时记录覆盖区间、上一版 ID、消息 digest 和输入哈希，重试同一区间不会写两份。原始消息始终保留，摘要只是可重建投影。摘要调度不阻塞用户发消息；如果后台失败，后续触发或创作 Run 入口可以补齐，而不是让一次临时模型错误直接丢掉历史。 [P2] [P4]

### Q47. 长期记忆里出现过时或错误事实怎么办？

**可直接回答：**我不会用“最近写入的记忆覆盖旧记忆”这么简单的规则。首先要看记忆来自哪个 Artifact、哪个版本，是用户明确约束、模型摘要还是外部参考。作品事实一旦因上游剧本修订而失配，相关下游状态应标为 stale 并重算；冲突的会话摘要要保留来源、停止当成确定事实使用。模型可以提示冲突，但不能自己决定把两个互斥设定合并。这样回答的重点是来源、有效范围和纠错路径，而不是只谈向量库里删一条记录。 [P4] [I01]

### Q48. 角色「知道」和作者「计划让角色知道」有什么区别？

**可直接回答：**“作者计划让角色在第五集知道秘密”与“角色在第三集已经知道秘密”不是同一件事。如果把前者当事实放进当前上下文，角色就会未学先知。项目用 EpisodeDelta 区分已发生事实、角色已知、道具变化、伏笔和未来计划，服务端按集数和版本演算 ContinuityState；Writer 只读取写本集之前已经成立的状态。确定性剧情基准也分别检查知识越界和未来计划泄露，真实模型生成时仍要通过连续性校验和人审。 [P2] [P4]

### Q49. 为什么让 LLM 输出 typed delta，而不是直接覆盖整个连续性状态？

**可直接回答：**让模型每集重写全部剧情状态，很容易漏掉早先事实，也很难判断哪一条是它新编的。我要求模型只输出本集发生的 typed delta，包括变化类型和引用；服务端再做来源校验、稳定 ID 分配和纯 reducer 演算。这样旧事实不会被随意覆盖，重放同一集也能得到一致状态。不过 typed delta 只是把错误限制在可校验的入口，不代表模型抽取一定正确，所以还需要对真实剧本逐条评估抽取质量。 [P2] [P4]

### Q50. ContextBuilder 怎样决定裁剪谁？

**可直接回答：**上下文预算不是简单截掉最早文本。ContextBuilder 先按任务确定必需材料：系统规则、用户当前约束、目标稿和必要前态；摘要与 RAG 再按优先级进入。可选片段超预算可以裁剪，并在 Manifest 里记录删了什么；如果当前目标稿或必要前态放不下，就明确报 CONTEXT_TOO_LARGE，不能给模型半份稿件却继续让它修订。这个策略既控制 token，也保护任务语义，后续可用消融实验检查裁剪有没有损害质量。 [P1] [P4]

### Q51. 为什么 ContextManifest 有价值？

**可直接回答：**ContextManifest 相当于一次模型调用的“上下文装箱单”。它记下用了哪版稿件、哪些摘要和 RAG chunk、估算 token、预算及裁剪原因。用户问“为什么这次忘了早先限制”，我可以沿着这张清单区分是原始消息未进摘要、检索没命中、版本选错，还是预算把片段裁掉，而不是盲目改 Prompt。Manifest 只能证明内容被提交进请求，不能证明模型真正理解或遵守，后者仍需结果评测。 [P1] [P4]

### Q52. 如何证明 Memory 真的带来了收益？

**可直接回答：**要证明 Memory 有收益，我会固定对话和剧情真值，只换记忆策略，比较无记忆、最近窗口、旧摘要和结构化策略。指标要同时覆盖写入正确性、约束召回、否决项、最新事实、下游使用、token 成本与跨项目泄漏。项目在 96 条消息的确定性基准中，旧策略约束召回为 0，结构化策略为 93.8%，相对完整历史节省 82.7% token；剧情组违规从 219 降到 0。摘要器是 FakeLLM，真实模型与人工质量验证尚未完成，我不会把这些数字说成线上效果。 [P4]

### Q53. Redis 短期窗口丢失会导致记忆丢失吗？

**可直接回答：**Redis 只保存短期窗口缓存，原始消息在 PostgreSQL；缓存丢失或连接失败时，可以按会话从数据库回源。累计摘要也作为持久化 Artifact 保存，剧情状态与确切作品版本绑定。因此 Redis 故障不应造成唯一记忆丢失。更细的风险在后台摘要任务：若进程退出使调度丢了，创作 Run 进入时必须检查并补齐覆盖区间。恢复能力需要通过故障注入和回源测试验证，而不是只说“缓存能重建”。 [P1] [P4] [P10]

### Q54. 多会话的项目级记忆怎样合并？

**可直接回答：**多会话合并不能拿各会话的 message sequence 直接比较大小，因为序号只在本会话内有意义。我的做法是分别取每个会话的最新累计摘要，在项目级预算内合并，并让确定版本的作品事实始终覆盖摘要。若当前任务明确来自某一会话，理论上应优先考虑这个会话；项目当前创作 Run 尚未把 conversation_id 作为优先锚点传入，这是已知边界。面试里我会说明已有合并方式，以及下一步如何防止跨会话的旧约束误导生成。 [P2] [P10]

## 第六部分：Agent 评测与实验（Q55-Q67）

### Q55. 软件测试与 Agent 评测有什么不同？

**可直接回答：**软件测试主要验证确定性合同，例如接口状态、权限、幂等和恢复；Agent 评测还要面对模型输出的随机性、主观质量及目标是否真正达成。我的做法是分层：先用单元和 E2E 测状态机，再用标注数据评 Planner 的意图、目标和澄清，再用真实模型重复运行评质量、成本和稳定性，最后才看用户采纳等线上业务指标。项目已完成不少确定性测试，但不能用测试通过率代替真实模型任务成功率。 [P3] [P6] [O3]

### Q56. 如何评意图识别？为什么不能只报准确率？

**可直接回答：**意图识别不能只报 overall accuracy。多数类占比高时，模型即使错过少量高风险写操作也可能看起来很准。我会分 turn_type、intent、目标类型、集数和批次报告 precision、recall、F1，再单独统计应澄清却执行、过度澄清和同键异参等业务风险。项目的评分器就是分层计分，目标集数错会触发独立失败门槛；这样能发现“意图名字对了，但改错集”的问题。 [P3]

### Q57. 数据集怎样避免被 Prompt「偷看」？

**可直接回答：**评测集要有开发集与冻结的盲测集，不能把盲测题目复制到 Prompt 示例里，也不能看着单条盲测失败反复调词。项目当前有 240 条开发集和 120 条 holdout，契约检查会验证后者原文未进入 Planner 模板。候选 Prompt 先在开发集调，再冻结版本整体跑盲测；还要去重、按请求类型和难度分层，并记录失败原因。这样才能把回归数字解释为泛化证据，而不是对题库的记忆。 [P3]

### Q58. 360 条评测集是否意味着当前模型精度有保证？

**可直接回答：**360 条代表我们有一个覆盖多类命令的评测资产，不代表模型已经在这 360 条上达标。当前 dataset v4 与 Prompt v1.4 的真实模型联合评测还没完成；旧的 60 条 v1.3 实验只能作为历史趋势，不能拿 create_script 的 96.8% F1 当现在整体准确率。我会先检查标签、评分器和盲测保护，再用固定 provider、参数和重复次数跑真实模型，报告每类指标、置信区间和坏例，最后才谈发布门槛。 [P3]

### Q59. LLM-as-a-judge 最大的风险是什么？

**可直接回答：**LLM-as-a-judge 最危险的是把同一模型的偏好当客观真值。它可能受措辞、答案长度、顺序和自我偏好影响，也可能给出看似合理却找不到原文证据的解释。我会先固定 Rubric，给评分器做人工标注集和一致性测试，再让它引用具体片段；对可机器验证的字数、版本和角色出场由程序检查。模型判断适合辅助排序和发现问题，不应独自决定“剧本质量合格”或“用户目标完成”。 [P5] [O3]

### Q60. 项目如何避免「模型自报总分」？

**可直接回答：**剧本质量不能让模型自己报一个总分就结束。项目把评分拆成九个维度、五档锚点，每项要求给出作品里的证据，再由服务端做证据位置和权重计算的验证；可确定的结构条件单独检查。这样能回答“为什么低分、该改哪一段”，也降低总分漂移的影响。但证据存在不等于审美结论一定对，真实模型下还需人工复核与评分一致性实验。 [P5]

### Q61. 模型引用了剧本中不存在的一句话，怎么处理？

**可直接回答：**如果评分器引用了稿件里不存在的一句话，我会把这条证据判为无效，而不是因为结论听起来合理就接受。可以先做严格原文定位，再允许有限的规范化或片段匹配，并记录引用对应的 Artifact 版本；无法定位的维度不给通过，要求重评或进入人工复核。项目的 Rubric 设计已把证据验证放进流程，但真实模型的证据来源率尚未跑出报告，所以不能宣称幻觉引用已被彻底解决。 [P5]

### Q62. 为什么对创作质量不能只用 BLEU/ROUGE？

**可直接回答：**BLEU 和 ROUGE 衡量与参考文本的词面重合，适合某些有标准答案的任务，却不适合开放式短剧创作：同一个剧情目标可以有很多好写法，词面相近也可能故事不成立。我会把评测拆成结构性约束、剧情连续性、引用忠实度、分维度人审和作者采纳；自动指标负责可确定部分，主观质量用带证据的 Rubric 辅助判断。若面试要求一个总分，我会先说明它的构成和权重，避免把单一分数当真实创作价值。 [P5] [O3]

### Q63. 如何设计一个有说服力的消融实验？

**可直接回答：**消融实验要一次只换一个因素。比如验证结构化 Memory，我会固定任务、稿件、模型、Prompt、温度和预算，只换记忆策略，比较约束召回、角色知识错误、token 与延迟；验证 RAG 则比较无检索、当前向量检索和候选混合检索。样本需要按长度、题材和错误类型分层，重复多次并报告最差值或波动。项目已有 FakeLLM 记忆对照，下一步是把同样设计迁到真实模型并加人工核验。 [P4] [O3]

### Q64. 线上 A/B 与离线评测分别解决什么问题？

**可直接回答：**离线评测适合控制变量、重复定位坏例、拦截发布回归；线上 A/B 才能检验真实作者是否接受、是否省时间、是否产生新的使用问题。两者的分母也不同：离线任务成功率不能直接当用户采纳率。当前项目有离线数据集、确定性测试和本地性能数据，没有线上 A/B 或真实用户采纳率。我会先把离线模型质量跑稳，再定义用户层面的完成时间、修改轮次和采纳行为，避免过早用单次满意度替代业务价值。 [P3] [P10]

### Q65. 发布门槛应看平均值还是最差值？

**可直接回答：**发布门槛不能只看平均值，特别是误改集数、跨项目泄漏这类低频高损失错误。项目的真实模型 harness 设计了同配置重复运行，并按最差一次和关键分类门槛判定；同时看写操作 precision、澄清召回、目标集数和批次等指标。均值可用于观察总体趋势，但只要关键安全门槛失败就不应发布。这里要说清这是评测方案，当前新版真实模型还没跑完，不能说门槛已经通过。 [P3]

### Q66. 如果 Prompt 改进了创建意图，却使修订召回下降，怎么判断？

**可直接回答：**如果 create_script 提升而 revise 召回下降，我会先确认标签、数据分布和评分器没有变，再看 revise 的坏例属于指代不清、缺当前稿、目标解析错误，还是 Planner 把它判成解释。不同错误成本不同，不能用整体 F1 的提升覆盖“本来该修订却没修订”。若修订是重点场景，我会设独立门槛，必要时回滚 Prompt 或做明确的场景路由。项目旧版评测就显示单一类别高分不足以代表联合合同达标。 [P3]

### Q67. 面试官问「你们的 Agent 完成率是多少」，怎么回答？

**可直接回答：**我会先问“完成率”指哪一层：Run 是否进入终态、用户指定目标是否有证据达成、作品是否被作者采纳，还是线上任务是否真正闭环。项目目前可以给出确定性 Outcome 规则 26/26、使用 FakeLLM 的 E2E 65/65，以及旧版单项模型实验；这些都不是当前真实模型的联合任务完成率，也不是用户采纳率。若要报一个可对外的 Agent 完成率，需要固定任务集、真实模型重复运行、结果证据检查和人工抽样，然后清楚写明分母与失败分类。 [P3] [P4] [P11]

## 第七部分：LLM 原理、训练与推理（Q68-Q83）

> 本节是算法岗与部分应用岗常问的**理论准备**。DramaAgent 使用外部兼容模型 API，没有在本项目中训练 Transformer、运行 LoRA/PPO/GRPO 或部署 vLLM。回答原理时要明确「我理解/我会这样实验」，不能改成「项目已实现」。近六个月的商汤算法应用、字节应用实习面经和算法岗 JD 都覆盖其中部分主题。[I06] [I08] [J02]

### Q68. Self-Attention 公式是什么，复杂度来自哪里？

**可直接回答：**Self-Attention 的单头计算是 `softmax(QKᵀ/√d_k)V`：输入先投影为查询、键和值，当前位置对所有可见位置算匹配权重，再加权汇聚信息。若序列长度为 n，显式注意力矩阵有 n×n 个元素，长上下文会带来计算和内存压力；多头是在不同投影空间并行学习关系。这里我会区分数学复杂度与工程实现：FlashAttention 等实现通过分块和 IO 优化降低内存占用，不能简单说所有服务都真的存一整张 n×n 矩阵。 [O9] [O22]

### Q69. Q、K、V 各自直观代表什么？为什么除以 √d_k？

**可直接回答：**Q 可以理解为当前位置想找什么，K 是各位置可供匹配的线索，V 是最终要汇聚的内容；三者都是从隐藏状态学习出来的投影，不是预先固定的“问题、关键词、答案”。Q 与 K 的点积决定注意力权重，若维度 d_k 增大，点积的方差也容易增大，softmax 可能饱和、梯度不稳定，所以要除以 `√d_k`。这套机制让模型能按上下文动态选择信息，但不意味着它天然知道哪些外部事实是真的。 [O9]

### Q70. 自回归模型的 causal mask、prefill 和 decode 怎么理解？

**可直接回答：**自回归模型生成第 t 个 token 时不能偷看未来，因此使用 causal mask。推理可以分成 prefill 和 decode：prefill 并行处理已给定的输入并建立各层 K/V，decode 再逐 token 生成，复用 KV Cache 而不是每步重算全部历史。长 Prompt 主要拖慢 prefill，长回答主要增加串行 decode 时间。项目曾遇到长 Story Bible JSON 被输出上限截断，所以应用层必须分别管理输入预算、输出预算和请求超时。 [O9] [P11]

### Q71. KV Cache 为什么影响推理吞吐？vLLM/PagedAttention 解决了什么？

**可直接回答：**KV Cache 保存每个请求已生成 token 的历史 K/V，避免 decode 时重复计算，但并发请求的长度不同，会形成大量动态显存分配和碎片。PagedAttention 把这些缓存分页管理，让物理块更灵活地分配和共享，提高显存利用率，从而支撑更多并发请求。vLLM 是一种推理服务实现，DramaAgent 当前调用外部兼容 API，没有部署它。若以后自托管，我会用相同请求集比较首 token 延迟、整体吞吐、显存、成本和模型兼容性，不只看峰值 tokens/s。 [O15]

### Q72. Temperature、top-p、max_tokens 分别影响什么？

**可直接回答：**temperature 改变采样分布的尖锐程度，值越高通常越发散；top-p 只在累计概率达到阈值的一组候选里采样；max_tokens 则限制最多生成多少输出 token。对于意图规划和结构化抽取，我会控制随机性并强校验 Schema；创作正文可以给适度多样性，但角色设定和任务预算不能松。max_tokens 也不是越大越好，过小会截断 JSON，过大可能超 provider 限额或放大成本。项目相关参数需要按任务和模型实测。 [P11] [O4]

### Q73. 为什么模型会幻觉？项目如何控制？

**可直接回答：**大模型是按训练分布预测后续文本，流畅不等于外部事实正确。在 DramaAgent 里，幻觉可能是编造不存在的原文引用、让角色提前知道秘密，或把“计划完成”说成“结果已达成”。我分别用来源绑定、低权威 RAG、结构化状态、证据验证、确定性 Outcome 和人工确认来约束这些错误。每一道只能降低某类风险，不能承诺零幻觉；真正的效果还要在固定坏例和真实模型生成上测。 [P1] [P5] [P7]

### Q74. JSON mode、JSON Schema 约束输出、Pydantic 后验校验有何不同？

**可直接回答：**JSON mode 主要约束输出是合法 JSON，不能保证字段一定符合业务要求；原生 Structured Outputs/JSON Schema 可以在生成过程中限制字段结构；Pydantic 是应用侧的后验类型和业务校验。项目主要是把 Schema 放进 Prompt，模型返回后用 Pydantic 校验，失败时有限次数反馈重试，并不是完全依赖原生受约束解码。即便换成原生 Schema，项目归属、目标版本、权限和语义一致性仍得由服务端验证。 [P1] [O4]

### Q75. 遇到 `finish_reason=length` 应该怎么处理？

**可直接回答：**我会先看 provider 的 `finish_reason`。如果是 `length`，问题本质是输出被截断，不能把它当普通 JSON 语法错误，拿同一配置盲目重试。先记录输入和输出 token、上限及目标任务，再决定缩短上下文、提高合法输出上限或把任务拆成更小阶段。项目曾有 Story Bible JSON 在 4096 token 上限处截断，解析层重复重试约五分钟；后来客户端直接识别截断并给出明确错误。这比仅加重试次数更有效。 [P11]

### Q76. RAG 与微调如何选择？

**可直接回答：**我会先看要改变的是“模型知道什么”，还是“模型如何稳定做事”。项目文档和稿件不断更新、还要版本与权限隔离，优先用 RAG 或受控上下文；若模型长期在固定格式、领域表达或动作策略上犯同类错误，且有高质量样本，再考虑 SFT 或 LoRA。两者能组合，但都要有同一套固定评测，比较质量、成本和维护代价。DramaAgent 当前没有微调实验，我不会说微调已经提升了创作质量。 [P1] [O10]

### Q77. LoRA 的核心公式和关键超参是什么？

**可直接回答：**LoRA 冻结原模型权重 W，只训练一个低秩增量，常写作 `ΔW=BA`，其中秩 r 远小于原矩阵维度，所以可训练参数和优化器状态更少。实际设计要决定插在哪些投影层，以及 r、alpha、dropout、学习率和训练数据质量；r 增大并不保证任务指标变好。若让我为项目规划实验，我会先针对稳定的 Planner 错误建立训练和盲测集，再比较 Prompt、LoRA 的质量与成本。当前项目没有训练 LoRA，也就没有自己的 r 参数结果。 [O11]

### Q78. QLoRA 与 LoRA 差在哪里？

**可直接回答：**QLoRA 仍然训练 LoRA 适配器，但把冻结的基座模型放在低比特量化表示里，原论文使用 4-bit NF4、双重量化和分页优化器来降低显存需求。它的价值是让有限显存下的模型适配更可行；代价是量化、吞吐和精度都需要实际验证，不能只按显存数字选。DramaAgent 使用外部模型 API，没有在本项目里部署基座模型，也没有 QLoRA 微调记录，因此我会把它作为训练方法解释，而不写成项目成果。 [O12]

### Q79. RLHF/PPO 里的 Actor、Critic、Reward、Reference 各做什么？

**可直接回答：**在典型 RLHF 的 PPO 流程里，Actor 是待优化的生成策略，Reward Model 近似人类偏好，Critic 估计价值以降低策略梯度方差，Reference 是保持策略不要偏离太远的基准；PPO 通过裁剪更新控制步长，并常配合 KL 约束。Agent 应用层的自我评估或反思不是 RLHF，因为它没有按这些训练信号更新模型参数。项目目前做的是应用层评测和修订，不涉及 PPO 训练；如果被追问，我会明确区分推理时工作流与训练时策略优化。 [O16]

### Q80. DPO 与 PPO、GRPO 有什么区别？

**可直接回答：**PPO 通常需要奖励信号、价值估计和在线采样；DPO 从成对偏好数据直接优化候选相对参考策略的偏好，省去显式 Reward Model 加 PPO 的部分训练环节；GRPO 用同一问题下多条输出的组内相对奖励构造优势，减少对独立 Critic 的依赖。它们的关键差异不只是公式，而是奖励是否可靠、偏好数据怎么来、训练稳定性和资源成本。DramaAgent 现有命令评测集不能直接当偏好训练集，若要后训练，必须重新设计偏好标签和盲测防泄漏。 [O13] [O14]

### Q81. 怎样选择大模型、轻模型及动态路由？

**可直接回答：**选模型我会先按任务拆开，而不是给整个 Agent 一种型号。preflight 能确定性判断的就不用模型；Planner、Writer、Evaluator、Reviser 对准确性、创作质量、延迟和费用的权重不同。先用固定任务集量各模型质量、错误类型、token、p95 和失败率，再考虑按难度或风险动态路由；对写操作，回退到弱模型也要重新过确认和校验。项目已支持按角色配置模型，但没有经过实验验证的在线动态路由策略，我不会把“可配置”说成“已优化”。 [P1] [I06]

### Q82. 什么时候做 SFT，数据该如何构造？

**可直接回答：**做 SFT 的前提是错误模式稳定、目标可重复标注，并且 Prompt、规则和 RAG 已经不足以解决。数据要包含正确输入输出、困难负例和冲突场景，按项目、用户或时间切分，避免近似重复样本同时出现在训练和评测里；指标也要看真实任务合同，不只看训练 loss。DramaAgent 的 360 条命令数据目前是评测资产，不能直接说已经拿去微调。若要开始，我会先补高风险误执行和目标错位样本，再设冻结盲测集比较微调前后。 [P3] [O17]

### Q83. 长上下文模型能替代 Memory/RAG 吗？

**可直接回答：**更长上下文能减少部分切分，但不能自动处理版本过期、来源权威、跨项目权限，也不能消除 token 成本和模型对早期约束的忽略。对本项目，当前目标稿、结构化角色知识和来源可追踪的摘要仍然重要；RAG 则负责只取本次任务相关的外部参考。我的实验基线会包括“全历史直接塞长上下文”，再比较约束召回、剧情连续性、质量、费用和延迟。如果长上下文在某些场景更简单且效果更好，就应该保留这一选择，而不是机械地维护复杂 Memory。 [P4]

## 第八部分：生产工程、安全与后端基础（Q84-Q97）

### Q84. LLM 请求失败时如何区分重试与立即失败？

**可直接回答：**我先按错误是否可能在短时间内自行恢复分类。429、连接超时和部分 5xx 可以限次指数退避，并尊重 provider 的 `Retry-After`；401、403、参数非法等配置或请求错误不应原样重试。Schema 不合法可以带具体校验反馈做有限重试；`finish_reason=length` 则要调整输出预算或拆任务。项目曾把模型 4xx 当临时错误，导致长时间无效重试，后来改成可诊断的失败路径。重试还要在预算与幂等边界内，避免一次用户请求放大成多倍费用。 [P2] [P11]

### Q85. 如何控制 Agent 的成本和延迟？

**可直接回答：**我会先把耗时和成本拆成模型调用次数、输入/输出 token、检索、数据库、队列等待与前端事件延迟。优化顺序是先去掉不必要的模型调用，再裁剪低价值上下文、按任务配置模型、缓存可复用的确定结果，最后才考虑并发和基础设施扩容。每个 Run 应有费用与时间预算，超限后有明确终态。项目目前的预算主要依赖进程内计数，多实例时还需共享存储；现有 API 和 SSE p95 测试不包含 LLM，不能用来宣称剧本生成很快。 [P6] [P10]

### Q86. 线上 Agent 应监控哪些指标？

**可直接回答：**我会把监控分成四层：业务层看任务达成、人工接管和作者采纳；模型层看错误率、截断、token、费用与延迟；执行层看 Run 排队、租约接管、重试、卡门和恢复；质量层看引用有效率、目标错位、连续性违规与跨项目泄漏。每次模型调用和 Artifact 都应带 trace、项目、Run、版本及 Prompt 标识，方便从投诉回溯到具体上下文。项目有运维诊断与轨迹设计，但线上采纳指标还没有真实数据，不能用离线测试填充。 [P1] [P8] [P10]

### Q87. 为什么要记录轨迹，而不只看最终答案？

**可直接回答：**只看最终答案会漏掉关键失败过程：模型可能选错目标后碰巧生成了看似合理的文本，或不断重试、消耗大量 token 后才成功。轨迹应记录用户输入、预检、Planner 决策、Action 确认、Run 节点、工具调用、使用的 Artifact 和 ContextManifest，以及最终 Outcome。这样我能把错误定位为规划、上下文、检索、执行还是评估问题，并做针对性回归。记录时要控制敏感内容和保留期限，不能为了可观测性把全部原始稿件随意暴露。 [P1] [P8] [J01]

### Q88. FastAPI 的 async 能让模型请求无限并发吗？

**可直接回答：**FastAPI 的 async 能在等待 I/O 时让事件循环处理其他请求，但它不是无限并发。模型 provider 有并发与速率限制，本地还有连接池、Worker 数、CPU 工作和内存约束；同步阻塞代码若跑在事件循环上，还会拖慢所有请求。我的设计是把长创作从 HTTP 请求路径移到持久化 Run 和 Worker，接口快速返回状态，前端通过 SSE 观察进度。压测要分别看 API、排队时间和模型端到端耗时，而不是只量接口响应。 [P1]

### Q89. PostgreSQL 的 `SKIP LOCKED` 有什么风险？

**可直接回答：**`SKIP LOCKED` 适合多个 Worker 从同一张队列表领取不同 Run，避免互相等待；但它返回的是跳过被锁行后的视图，不保证严格全局公平。某些任务可能长期被跳过，租约到期、重试和优先级也会影响顺序。因此我要有 owner、过期时间、领取时间、尝试次数与卡队列告警，必要时按年龄或优先级调度。它解决并发领取，不解决业务幂等、外部模型调用重复或队列积压本身。 [P1] [O6]

### Q90. Redis Pub/Sub 能保证事件送达吗？

**可直接回答：**Redis Pub/Sub 没有持久消费确认，订阅方断线时消息可能丢。因此项目不能把它作为事件唯一来源：Run 事件先写 PostgreSQL，Redis 只是通知 SSE 尽快推送；客户端重连带 Last-Event-ID，从数据库补遗漏，再进入实时流。前端还要按事件 ID 去重，因为补发与实时推送可能重叠。这样的设计可以接受 Redis 的低延迟优势，同时把恢复语义放在可持久化的数据上。 [P1] [I02]

### Q91. 如何防跨项目数据访问？

**可直接回答：**所有读取和写入都应从已认证用户与项目关系出发，再限定 Artifact、Run、消息和知识 chunk 的 project_id，不能信任客户端传来的资源 ID。对 RAG，过滤必须在数据库检索前做；对 Action 确认，还要复核目标版本和归属；对缓存键、SSE 订阅和导出也要保持同样作用域。项目有项目级边界，但多用户认证与团队权限仍有待完善，因此我会把当前测试覆盖和真正多租户上线要求分开说。 [P7] [P10]

### Q92. Prompt 注入与普通恶意输入的区别？项目边界在哪里？

**可直接回答：**普通恶意输入是用户直接要求系统做不该做的事；Prompt 注入更典型的是低权威材料，例如上传文档、网页或工具返回值，试图伪装成系统指令，让模型越权。项目把这些内容作为数据拼接，服务端对写操作另有白名单、权限和确认门；然而模型仍可能在文本生成上受影响，所以需要注入坏例、输出检查和人工复核。防线的核心是权限不交给模型，模板分隔只能辅助，不能宣称完全解决。 [P7] [O8]

### Q93. 为什么导出要冻结版本？

**可直接回答：**导出不是“拿当前最新文本拼一下”那么简单。剧本可能在导出开始后被修订，如果每次查询都取最新版本，最终文件会混入不同时间的稿件。项目在导出前冻结选定的 Artifact ID 和版本，之后按这个快照读取、生成文件并记录来源。这样用户能解释“这份导出基于哪一稿”，也便于复现和审计。若版本被作者更新，新的导出应另起一次请求，而不是悄悄改变已经开始的导出内容。 [P2] [P1]

### Q94. 该怎样测试一个 LLM 应用？

**可直接回答：**我会把 LLM 应用测试做成分层金字塔。最底层用单元测试验证解析、权限、幂等、预算、reducer 和 Outcome；集成测试接真实 PostgreSQL/Redis，覆盖租约、回源和事件；E2E 用 FakeLLM 验完整旅程；再用冻结数据集和真实模型重复评 Planner、检索和创作质量，最后加人工评审与线上指标。每层说明它能证明什么：65/65 FakeLLM E2E 可以证明流程稳定，不能证明真实模型输出质量。 [P3] [P6] [P11]

### Q95. 如何排查「用户确认了计划，但一直看不到结果」？

**可直接回答：**我会沿请求链找最后一个持久证据：Turn 是否成功写入，Action 是否处于待确认或已确认，确认时版本是否 stale，Run 是否 queued、running 或卡在人工门，Dispatcher 是否拿到租约，节点是否写了 Artifact，SSE 是否漏了通知。若数据库里 Run 已完成而页面没更新，重点看事件回放和前端订阅；若 Run 还 queued，查 Worker、租约和模型限流。每一步用状态与时间戳定位，避免先改 Prompt 或让用户无限刷新。 [P8] [P11]

### Q96. 10 GB 文件上传、深分页这类后端题与你的项目有关系吗？

**可直接回答：**这类问题与项目有关，因为 LLM 应用最终仍是后端系统，但我会先说明当前上传限制和实际规模。若真要支持 10 GB 文件，不能把整个文件放内存或一次 HTTP 请求里；应做分片上传、校验、断点续传、对象存储临时态和异步摄取，再把文档版本与项目权限写入数据库。深分页也不宜长期用大 OFFSET，可按稳定排序键做游标分页。这里是扩展设计，不是 DramaAgent 当前已支持的能力。 [P1] [I12] [I13]

### Q97. 可能手撕哪些题，怎么准备？

**可直接回答：**应用岗可能让我手撕并发、缓存或数据结构，算法岗也可能问 top-k、LRU、队列和字符串处理。我会先把题目约束、复杂度和边界问清楚，再给能运行的实现与测试用例。若题目贴近项目，例如设计幂等键存储、合并有序事件、计算检索指标或找失配版本，我会用项目里的真实数据语义解释算法选择。准备时不能只背 Agent 术语，Python/Java 基础、SQL 索引和 Redis 一致性也需要过关。 [I02] [I03] [I05] [I12]

## 第九部分：系统设计与高压追问（Q98-Q107）

### Q98. 请现场设计一个「长文档研究 Agent」，你先问什么？

**可直接回答：**我会先问用户要的研究结果、可用资料范围、时效、引用要求、预算、截止时间，以及是否允许访问外网。架构上把任务拆成计划、检索、证据抽取、冲突核验和报告生成，检索结果保留 URL、时间和片段，报告里的关键结论必须能回溯证据。每轮检索由覆盖缺口和预期信息增益驱动，不能无限搜索；失败时给出已核实与未核实部分。若是多用户产品，还需权限隔离、配额、可恢复任务和人工确认对外发布的内容。 [I07] [J01]

### Q99. Deep Research 什么时候停止检索？

**可直接回答：**Deep Research 不该靠固定轮数停，也不该让模型一句“我觉得够了”就停。我会先把研究目标拆成必须回答的子问题，跟踪每个问题的证据覆盖、来源独立性、冲突和最新检索的信息增益；当关键问题已有足够可靠证据、连续几轮没有新增事实，或预算与截止时间到达，就停止。仍有空白时要在报告里标出未核实，而不是用生成文本补齐。阈值应在固定研究任务集上校准，避免对简单题过搜、复杂题早停。 [I07] [O1]

### Q100. 如果面试官说「你的项目只是调 API」，怎么回应？

**可直接回答：**如果说“只是调 API”，我会承认模型能力来自外部服务，再具体解释工程难点不在 HTTP 调用本身。这个项目要把含糊请求变成有权限的动作，在多稿并存时锁定目标，跨多集保持连续性，在超时或崩溃后恢复，并让评分、修订和导出能追溯同一版本。我可以展示 Turn 到 Artifact 的状态链、幂等与故障测试，以及 Memory 的离线对照结果。同时也会承认尚未证明真实用户效率提升；不靠夸大模型能力回答这个质疑。 [P3] [P4] [P11]

### Q101. 你的方案比「一个 Prompt 直接生成剧本」有效多少？

**可直接回答：**我目前不能给出“比一个 Prompt 快多少、好多少”的真实模型数字，因为当前还没有完成同模型同任务的基线实验。合理的比较是固定题材、目标集数和约束，用同一模型与预算分别跑单 Prompt 和分阶段方案；盲审连续性、可改性、角色知识错误、作者采纳、总 token、耗时与失败恢复。现有项目数据能证明分阶段链路可用，Memory 的确定性基准显示约束保留改善，但不能直接推断最终剧本质量一定优于单 Prompt。这是我下一步最重要的实验。 [P1] [P3] [P4]

### Q102. 讲一个你亲自定位的复杂故障。

**可直接回答：**我会讲一次长结构化输出被截断的故障：Story Bible 生成返回的 JSON 不完整，表面上看像解析器偶发失败，但检查 provider 的 `finish_reason` 发现请求触发 4096 token 输出上限。旧代码把它当可恢复解析错误，用同样配置重试，约五分钟都不会成功。修复时我在 LLM 客户端先识别 length，返回明确错误，再按任务调整输出预算或拆分内容；回归测试覆盖截断响应。这个案例让我认识到要先看模型协议层的失败原因，再决定是否重试。 [P11]

### Q103. 如果要把 DramaAgent 部署给多个团队，先改哪三件事？

**可直接回答：**若要给多个团队使用，我会先补三件事。第一是身份认证、团队和项目级授权，并让 RAG、SSE、导出和缓存键都沿同一权限边界；第二是把进程内预算、限流和 Worker 配额做成跨实例可共享的机制，避免某个团队占满模型额度；第三是完善运维观测和数据生命周期，包括费用、任务恢复、审计、删除与备份。当前项目的单项目写任务一致性设计仍有价值，但它不等于已经具备多租户生产能力。 [P1] [P10]

### Q104. 如果有两周时间继续改进，优先做什么？

**可直接回答：**如果只有两周，我先补真实模型评测，而不是立刻再加一个框架。第一周冻结 Prompt、provider 参数和命令盲测集，跑重复实验，定位目标错位、过度澄清与截断坏例；同时对 Memory 和 RAG 做少量可人工核验的端到端对照。第二周修最影响成功率的失败路径，补回归与可观测性，再看是否需要模型路由或混合检索。优先级以真实失败的频率、业务损失和修复成本决定；如果评测显示现有方案够用，就不增加复杂度。 [P3] [P4] [P10]

### Q105. 面试官要求你画一张架构图，应标哪些边界？

**可直接回答：**我会画五条边界：用户和前端，Turn/Planner/Action 的对话控制层，Run/LangGraph/Worker 的执行层，Artifact 与 PostgreSQL 的事实层，以及 RAG、Memory、外部模型和 SSE 的支撑层。图上标清人工确认门、模型调用在事务外、数据库租约、版本快照、幂等键和事件回放路径。再用一条“修改第 2 集”的请求走一遍，说明旧计划何时过期、状态如何恢复、评估引用哪一稿。这样架构图能解释失败语义，而不只是框架 Logo 的连接图。 [P1]

### Q106. 怎么解释你负责的部分与团队贡献？

**可直接回答：**我会按真实贡献说话：先指出自己负责的具体问题，再说设计与代码边界、取舍、验证数据和团队协作。比如若我负责 Run 恢复，就讲租约、Checkpoint、Artifact 去重和崩溃窗口；若我负责 Memory，就讲旧策略为何丢约束、结构化摘要怎么验证。未亲自做的模块我只说明接口和配合，不把整个仓库都说成个人成果。面试官往往会继续追问表结构、失败路径和测试，准确的职责边界比“大而全”更有说服力。 [I02] [I03] [J01]

### Q107. 你最想重做项目的哪一处？

**可直接回答：**如果重做，我会优先考虑单项目单活动 Run 和进程内预算这两个边界，但不会立即把系统拆成很多服务。当初先串行写同一作品，是为了守住版本与确认语义；预算放进程内，也便于先把调用链跑通。重构触发条件应是队列等待 p95、并发项目数、预算超限率等数据真的达到瓶颈。升级时我会把配额下沉共享存储，研究同项目只读任务并行，同时保留写操作的版本检查与幂等，避免扩容后出现更难恢复的错稿。 [P1] [P10]

## 第十部分：算法岗加试（Q108-Q110）

> 这些题来自算法应用面经中的分布式训练追问，属于原理储备，不是 DramaAgent 已经做过的工程实践。[I06] [J02]

### Q108. ZeRO 三个阶段分别节省什么？

**可直接回答：**普通数据并行让每张 GPU 保存完整参数、梯度和优化器状态，模型状态会大量重复。ZeRO 分阶段减少这种冗余：Stage 1 分片优化器状态，Stage 2 再分片梯度，Stage 3 连参数也分片；显存下降的代价是更多通信、参数按需聚合和调度复杂度。实际训练还要看激活显存、带宽和吞吐，所以“模型装得下”不等于“训练更快”。DramaAgent 没有训练集群，我能解释这个原理，但不会说自己在项目里用过 ZeRO。 [O20]

### Q109. 数据并行、张量并行、流水线并行怎样选择？

**可直接回答：**数据并行是每张卡放一份模型、把样本分开，模型能单卡容纳时最直观；张量并行把同一层的矩阵运算切到多卡，解决单层太大的问题，但层内同步频繁；流水线并行把不同层放到不同设备，用微批次提高利用率，却会有流水线气泡。大模型训练通常组合这些策略，选择取决于模型大小、单卡显存、节点内外带宽和目标批大小。我的项目用托管模型 API，没有这类并行实践，回答时会把理论判断与个人经历分开。 [O21] [O23]

### Q110. 训练 loss 下降，为什么 Agent 任务成功率可能不升反降？

**可直接回答：**训练 loss 降低说明模型更擅长预测训练分布里的 token，却不保证 Agent 在真实任务里选对工具、填对目标、正确澄清或恢复失败。数据泄漏、任务分布变化和格式过拟合，都可能让 loss 好看而任务成功率下降。如果将来为项目做 SFT，我会冻结一套真实任务集，比较误执行、目标错位、Schema 有效率、最终 Outcome、成本和人工坏例，并和未微调基线对照。当前项目没有训练曲线或微调后收益，这只能作为实验方案回答。 [P3] [O3] [O17]
