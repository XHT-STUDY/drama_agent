## 一、筛选结果与使用方式

上游报告收录 83 场第一方面经、51 个公司/业务线标签和 1,098 个机械切分的题目单元。按“能否从 DramaAgent 的业务、设计或代码自然追问出来”初筛后，有 600 余个单元相关；其中大量是同义问法或被网页压成一行的复合题。本文件将它们人工归并成 **20 张母题卡**。

每张卡包含：

- 赛文X面经中出现的典型问法；

- 面试官继续深挖时的速答；
- 项目证据和不能越过的事实边界。

不要逐字背诵。练习时先说结论，再讲一个项目机制、一个取舍和一个未解决边界。标记为 **A** 的题优先练到 60～90 秒；B 题练到能回答追问；C 题只需知道边界。

## 二、回答前必须记住的事实边界

1. DramaAgent 是“受约束的 Agent + 确定性工作流”，不是开放式多 Agent 自主协商系统。
2. LangGraph 在项目里主要承担长任务状态图和 checkpoint，不负责业务授权、版本语义或任务租约。
3. PostgreSQL 是事实源；Redis 是短期缓存和实时通知通道，丢失后可回源。
4. Artifact 内容不可变，修改通过新版本表达；评估、修订和导出绑定确切版本。
5. 当前工作流拓扑由代码预定义，不是让模型现场生成任意图。
6. 没有实现自主 Skill 学习、开放工具循环、任意代码执行或完整多 Agent 协作。
7. RAG、Memory、Prompt 和长上下文解决的问题不同，不能互相替代。
8. 1099 个后端测试、181 个前端测试和 E2E 使用 FakeLLM/FakeEmbedder，证明工程合同，不证明真实模型创作质量。
9. Prompt v1.4、dataset v4 的 360 条真实模型联合评测尚未执行；历史小样本结果不能冒充当前准确率。
10. 没跑过的线上 DAU、成功率、真实用户提效、线上 QPS 和生产 SLA，直接说尚未验证，再说明验证方案。

## M01｜项目解决了什么问题？为什么值得做？【A】

### 典型问法

- 介绍一下你的 Agent 项目，解决什么问题？
- 为什么不直接用大模型生成剧本？
- Agent 提效到底提谁的效率，收益是什么？
- 这个项目是 Demo，还是能完成完整业务闭环？
- 与普通 ChatBot 的区别是什么？

### 参考回答

DramaAgent 面向中文短剧创作。这个场景不是输入一句话、生成一篇文本就结束，而是要经历需求澄清、世界观和人物设定、大纲、分集剧本、评估、修订、版本比较和导出。直接调用 LLM 的主要问题有三个：长周期创作会遗忘早期设定；创作步骤和质量标准难以复用；中途失败或多轮修改后，很难确认当前稿件和修改依据。

我的方案是把自然语言交互作为控制面，把创作过程做成有状态、可恢复、可评审的工作流。模型负责理解意图和生成内容，服务端负责权限、版本、状态、预算和结果判定。系统现在可以从想法、大纲或文件输入开始，生成 Story Bible、十集大纲、前三集剧本，完成逐集评估、一次受限自动修订、连续性检查、版本 Diff 和导出。它已经证明了工程链路和确定性合同，但真实作者是否显著省时、成稿质量是否提高，还需要真实模型和用户实验验证。

### 继续追问速答

- **为什么算 Agent？** 因为系统要结合项目状态理解自然语言请求、形成受限计划并选择下一步，而不是固定表单直接调用接口；但执行权仍在服务端。
- **最大的业务价值？** 不是“替作者一次写完”，而是让长周期创作可持续修改、可找回依据、可从失败处继续。
- **与 ChatBot 的区别？** ChatBot 的中心是回复消息；这里的中心是可确认的 Action、可执行的 Run 和可追溯的 Artifact。

### 证据与红线

- 证据：[README](../README.md)、[架构讲解](ARCHITECTURE_WALKTHROUGH.md)。
- 不要说“已证明比直接使用 LLM 提升了多少质量”；当前没有真实用户 A/B 数据。

## M02｜整体架构和一条请求的完整链路是什么？【A】

### 典型问法

- 讲一下 Agent 平台的整体架构和分层。
- 用户输入一句自然语言以后，系统内部发生什么？
- 前端、Agent、工作流和存储之间怎样串起来？
- 每层职责是什么，为什么这样拆？

### 参考回答

系统可以分为交互控制、应用执行、工作流、模型能力、确定性工具和数据层。用户输入先形成 AgentTurn，作为输入和重试的收据；确定性预检先处理明显越界、冲突或歧义，再由 Planner 输出白名单内的意图、目标选择器和约束。服务端解析真实 Artifact、保存待确认 AgentAction 和源版本快照。用户确认后创建 WorkflowRun，Dispatcher 从数据库领取任务，LangGraph 按节点执行，生成的内容以 Artifact 版本写入 PostgreSQL。进度事件先持久化，再通过 Redis 和 SSE 推送。最后 Outcome 根据 Run 与 Artifact 证据判断目标是否达成，不相信模型自报“完成”。

这套拆分的核心是：Turn 记录用户说了什么；Action 记录系统准备做什么以及是否获得授权；Run 记录实际执行进度；Artifact 记录已经产生的业务事实。四者分开后，才能正确处理双击确认、任务崩溃、多稿并存和结果审计。

### 继续追问速答

- **模型调用放在哪？** Skill 内部，通过统一 LLMClient 返回结构化结果；不在数据库长事务中等待模型。
- **为什么不是前端直接调 LangGraph？** 前端不能承担权限、版本、幂等和恢复语义。
- **为什么是模块化单体？** 当前规模下减少分布式复杂度；边界已按服务、工作流、仓储和能力划分，未来可按瓶颈拆分。

### 证据

- [系统架构](ARCHITECTURE.md)
- [对话式 Agent 设计](../DESIGN.md)

## M03｜为什么是“Agent + Workflow”，而不是自由 ReAct 或多 Agent？【A】

### 典型问法

- Agent 和传统 Workflow 的本质区别是什么？
- 为什么选择 Plan-and-Execute？
- 为什么不用一个自由 ReAct Agent 完成全流程？
- 单 Agent、多 Agent、固定 Workflow 分别适合什么情况？
- 你的系统到底是 Agent，还是披着 Agent 外衣的工作流？

### 参考回答

我把系统定义成“受约束的 Agent 加确定性工作流”。自然语言请求存在歧义，用户也可能在不同作品版本上要求解释、续写或修改，所以需要模型参与意图理解和内容生成；但创作阶段、权限、版本、成本和终态可以明确建模，不适合交给开放式循环自由决定。

我选择 Plan-and-Execute，是因为写操作有持久副作用。模型先提出受限计划，服务端补全真实目标并让用户确认，之后由固定图执行，更容易控制过期计划、失败恢复和预算。多 Agent 只有在任务能有效并行、角色拥有独立信息或工具、合并结果可验证时才值得引入。DramaAgent 当前是一个编排器调用多个专业 Skill，没有多 Agent 协商的真实实现；我不会把 Skill 分工包装成多智能体。

### 继续追问速答

- **什么时候适合自由 ReAct？** 开放探索、步骤无法预先枚举、工具调用只读且错误代价较低时。
- **为什么不是普通 Workflow？** 用户的意图、目标稿和约束不是固定表单，需要结合上下文判断；但判断结果必须落回确定动作空间。
- **多 Agent 的最大代价？** 上下文同步、冲突裁决、延迟、Token 成本和错误传播。

### 红线

- 不要说项目已经实现 Leader Agent、Swarm 或 Agent Team。

## M04｜模型和服务端的职责怎样划分？【A】

### 典型问法

- 哪些步骤交给模型，哪些必须由代码控制？
- 模型识别错意图怎么办？
- Planner 为什么不能直接输出 Artifact ID、SQL 或任意工具名？
- 什么情况需要澄清，什么情况可以使用默认值？
- Agent 说执行成功了，怎么证明它真的执行了？

### 参考回答

我的原则是“模型有建议权和生成能力，服务端有执行权和事实判定权”。模型适合判断用户大致想做什么、生成设定和剧本文本、按 Rubric 给出带证据的语义判断；服务端负责项目归属、真实 ID 解析、版本新鲜度、预算、幂等、路由、分数计算和终态。

Planner 只能输出白名单意图、目标类型、集数和约束，不能直接授权 SQL、任意工具或数据库 ID。明显越界和冲突先由 preflight 拦截；猜错代价低的创作偏好可使用默认值，可能改错稿或扩大作用范围的请求必须澄清。执行完成后，Outcome 查询 Run 状态和实际 Artifact，不把模型生成的“已完成”当证据。

### 继续追问速答

- **Schema 能解决安全吗？** 只能约束形状，不能替代权限、版本和业务授权。
- **如何降低误执行？** 确定性预检、白名单计划、服务端目标解析、写操作确认、执行前再次校验。
- **怎样衡量意图识别？** 除总体 F1，还要单独统计“应澄清却执行”、目标集数错误和过度澄清。

## M05｜LangGraph、Runtime 和状态是怎样设计的？【A】

### 典型问法

- 为什么选择 LangGraph，不选择 LangChain 或自己写状态机？
- Agent Runtime 的核心能力是什么？
- 图上每个节点代表什么？状态存在哪里？
- 为什么不把正文直接放进 State？
- LangGraph 状态怎样流转和持久化？

### 参考回答

DramaAgent 的 Runtime 不只是一次模型循环，而是 Run 调度、状态图、持久化效果和事件交付的组合。LangGraph 适合表达创作中的阶段、条件路由、人工门和失败续跑；我用 PostgreSQL checkpointer，以 run_id 作为 thread_id 保存节点进度。

State 只保存 Artifact ID、集号、revision_round、completed_nodes 等轻量信息，完整剧本和评估在 Artifact 表。因为 LangGraph 每个节点后都会保存快照，如果把几万字正文放进 State，会在多个 checkpoint 中重复复制，恢复时也不需要这些副本。图负责“接下来执行哪个节点”，数据库中的 Action、Run 和 Artifact 负责业务语义。框架可替换，但这些业务对象不能依赖框架隐式状态。

### 继续追问速答

- **LangChain 和 LangGraph 的区别？** 前者更偏组件与调用链；后者更适合显式状态图、条件分支和持久化恢复。本项目选型主要由长任务恢复驱动。
- **节点是什么？** 一个有明确输入输出和副作用边界的阶段，例如 normalize、retrieve、story_bible、outline、write、evaluate、revise。
- **Runtime 是否等于 LangGraph？** 不等于；Dispatcher、租约、幂等、Artifact 和事件系统同样属于运行时。

## M06｜工作流是动态的吗？Agent Loop 怎样结束？【A】

### 典型问法

- 动态 Workflow 是怎么实现的？
- Workflow 偏确定还是偏自由？
- Agent 没有终止条件时怎么定义结束？
- 自动修订如何避免死循环？
- 哪些地方允许人工介入？

### 参考回答

当前项目不是让模型动态生成任意工作流。创作、评估、修订等图的拓扑由代码预定义，动态性体现在：用户意图选择哪个工作流、条件函数根据状态选择分支、阶段门决定是否暂停、以及是否进入修订。这样既保留任务适配能力，又能在上线前知道所有可能副作用。

项目没有开放式无限 Agent Loop。创建流程有明确终态；自动修订只选择最低分且满足条件的一集，`MAX_REVISION_ROUNDS=1`；重评掉分超过阈值会转人工复核。写操作在 Action 层确认，长流程还可以在大纲或剧本阶段停住等待用户。终止条件由服务端状态和证据决定，不由模型说“我觉得完成了”。

### 继续追问速答

- **为何限制一轮修订？** MVP 先限制成本和错误放大，等真实评测证明多轮有净收益再放开。
- **未来如何支持动态图？** 先定义允许节点、类型化边、预算和静态校验，再把候选图展示确认；不会执行任意模型生成代码。
- **人工门在哪里？** Action 写操作确认、阶段确认、连续性失败或修订变差后的人工复核。

## M07｜长任务如何暂停、恢复、取消和处理 Worker 崩溃？【A】

### 典型问法

- 长任务失败后能从失败点继续吗？
- Worker 或进程崩溃怎么办？
- 用户暂停、取消和续跑是怎么做的？
- 任务中断时怎样避免重复生成？
- 为什么需要租约、心跳和 checkpoint 三套机制？

### 参考回答

API 先创建 queued Run 并立即返回；Dispatcher 用 `FOR UPDATE SKIP LOCKED` 原子领取任务，写入 lease_owner 和 lease_expires_at，运行中通过心跳续租。Worker 崩溃后租约过期，其他 Worker 可以重新领取；LangGraph checkpoint 决定从哪个节点继续，Artifact/input_hash 和 completed_nodes 避免已完成阶段重复落库。

取消是协作式的：节点入口和多 Artifact 循环的安全点检查取消信号，保证取消后不继续写新产物；正在进行的第三方模型请求未必能立刻物理终止。阶段暂停与故障恢复也要区分：作者审稿是当前执行段正常结束，确认后创建下一段；进程崩溃才复用同一个 Run/checkpoint。

### 继续追问速答

- **Checkpoint 能保证只收费一次吗？** 不能。模型已返回但结果尚未持久化时崩溃，重试仍可能再次计费。
- **租约和 checkpoint 分工？** 租约决定谁有权执行；checkpoint 决定从哪里继续。
- **恢复耗尽怎么办？** 超过次数后明确失败并记录错误码，不能永远保持 running。

## M08｜幂等、并发和版本一致性如何保证？【A】

### 典型问法

- 用户双击确认会不会创建两个任务？
- 同一个请求重试多次怎样处理？
- 多个 Worker 会不会领取同一个 Run？
- 计划确认前作品已经被修改，旧计划怎么办？
- Checkpoint、input_hash 和数据库唯一约束有什么区别？

### 参考回答

幂等分三层。Turn 使用幂等键避免同一输入重复接收；确认 Action 时使用行锁，已确认请求返回原 Run；Run 和 Artifact 使用请求哈希、input_hash 与数据库唯一约束折叠相同副作用。多个 Worker 通过 `SKIP LOCKED` 和租约竞争任务，旧 Worker 不能在失去租约后越权收尾。

Action 生成时记录源 Artifact 的 ID、版本和 checksum。确认时重新读取当前有效版本；如果期间作品变化，Action 标记 stale，要求基于新稿重新规划。应用层预检查改善体验，数据库约束才是并发下的最终防线。这里保证的是业务效果尽量幂等，不承诺第三方模型调用 exactly-once。

### 继续追问速答

- **同一个幂等键但参数不同？** 返回冲突，不能静默复用旧结果。
- **为什么不能只靠 Redis 锁？** 事实和唯一约束在 PostgreSQL；Redis 丢失不能破坏正确性。
- **SKIP LOCKED 的风险？** 不保证绝对公平，需要任务年龄、尝试次数和积压告警。

## M09｜为什么采用不可变 Artifact？修改后怎样维护上下游一致性？【A】

### 典型问法

- 为什么更新内容时不直接覆盖旧稿？
- 评估报告、修订稿和导出怎样对应正确版本？
- 修改第二集以后，后续剧集和剧情状态怎么办？
- 版本 Diff 和来源追踪怎么做？
- 导出为什么也要冻结版本？

### 参考回答

剧本会被评估、修订、比较和导出，覆盖旧稿会让下游结果失去依据。因此每次变更都插入新的 Artifact 版本，内容不 UPDATE；评估通过 `evaluates` 指向确切剧本版本，修订通过 `revises/derived_from` 记录来源，导出保存冻结工作集。`input_hash` 用于识别相同输入的意外重放，用户主动要求重写则产生新版本。

上游版本变化后，下游不能悄悄继续沿用。旧 Action 会过期；后续剧情状态和衍生内容需要标记 stale、重算或让用户明确选择影响范围。当前项目已经能识别大纲修改对旧剧本的影响，但完整的“任意上游修改后自动重算所有下游”不是无限开放的，要根据成本和作者意图受控执行。

### 继续追问速答

- **为什么不只保留 latest 指针？** latest 无法说明评估当时看的是哪一稿，也无法审计或复现。
- **Diff 是否调用模型？** 剧本使用确定性场景/行级 Diff，解析失败回退全文行 Diff。
- **候选稿是否自动成为当前稿？** 不一定；生成、校验和作者采纳是不同状态。

## M10｜Memory 和长上下文怎样设计？【A】

### 典型问法

- 对话越来越长，怎么做上下文压缩？
- 长期记忆和短期记忆怎么划分，存在哪里？
- 为什么不能只保留最近 N 条消息？
- Skill、Memory、知识库和完整历史有什么区别？
- 如何避免压缩后“失忆”或错误事实长期污染？

### 参考回答

我不会把所有内容都叫记忆。原始消息完整保存在 PostgreSQL；Redis 只缓存最近消息窗口，丢失可回源。较早对话形成累计 Dialogue Summary，保留用户确认项、否决项、长期约束和未决问题；确定版本作品派生结构化 Story State，记录角色知识、伏笔、道具、关系和时间线；RAG 则是外部参考资料。

ContextBuilder 按任务分配预算，让当前用户请求、确切作品版本和必要剧情状态优先，摘要和 RAG 片段次之。辅助内容可显式裁剪，目标正文放不下就报错，不能静默给模型半份稿件。每次装配生成 ContextManifest，记录实际使用了哪些版本、摘要和 chunk，方便判断“忘记”来自写入、召回、裁剪还是模型未遵守。

### 继续追问速答

- **只保留最近 N 条为什么失败？** 很早但仍有效的否决项会被挤出窗口。
- **错误记忆怎么处理？** 按来源和版本判断权威；上游稿件变化后派生状态标 stale 并重算，模型不能自行合并冲突事实。
- **长上下文能替代 Memory 吗？** 不能完全替代；它增加容量，但不解决来源、权威、版本、选择和审计。

### 证据与红线

- [Memory 设计](MEMORY_DESIGN.md)、[领域语言](../CONTEXT.md)、[Memory 评测](MEMORY_EVAL_REPORT.md)。
- 93.8% 约束召回和 82.7% token 节省来自确定性/FakeLLM 基准，不是线上真实模型收益。

## M11｜RAG 和知识库如何实现、评测和隔离？【A】

### 典型问法

- 讲一下 RAG 全链路，为什么要单独做知识层？
- 文档怎样切片、向量化、召回和更新？
- 召回准确率不够、几十万文档时怎样优化？
- RAG 如何处理权限、过期知识和错误召回？
- RAG 能解决幻觉和 Prompt 注入吗？

### 参考回答

知识摄取链路是：文档解析、按标题层级切块、生成 embedding、带项目/类别/来源元数据写入 PostgreSQL + pgvector；文档和 chunk 使用 content hash 做增量幂等，未变化块可复用 embedding。创作时按项目和阶段过滤：Story Bible、大纲、剧本写作检索不同类别，再限制 top-k、每文档块数和上下文预算，并保留 retrieval trace。

评测必须把“是否找到正确证据”和“模型是否正确使用证据”拆开，分别看 recall@k、MRR、误召、引用回源和下游遵守。跨项目权限必须在查询层先过滤，再算相似度，不能全库召回后在应用层删除。RAG 只是低权威增强信息，不能自动防幻觉或注入；检索内容仍可能过期、错误或恶意。

### 继续追问速答

- **Chunk 大小怎么定？** 根据语义完整性、召回粒度和生成任务做分层实验，而不是只凭 token 常数。
- **为什么没有直接上 BM25 + reranker？** 当前先建立向量基线；只有坏例显示专有词漏召或正确候选排序靠后，才分别引入混合检索或重排并测成本。
- **向量库不可用怎么办？** 可选创作参考可降级并告警；用户要求严格依据指定资料时必须失败，不能凭常识补写。

### 红线

- 不要声称已经实现 BM25、RRF、学习型 reranker 或 HyDE，除非代码快照之后确实补齐并有测试。

## M12｜怎样评测剧本、处理 bad case 和自动修订？【A】

### 典型问法

- Agent 效果如何判断，评测集怎么构建？
- 模型自己打分可信吗？
- 你们怎样从 bad case 反推系统优化？
- 自动修订选择哪一集，怎么避免越改越差？
- 完成率、准确率、用户采纳率分别是什么？

### 参考回答

项目把评测分成三层：软件测试验证权限、状态和幂等；离线模型评测验证 Planner、Memory、RAG 和生成质量；线上业务评测才验证作者是否采纳、是否节省时间。三层不能互相冒充。

剧本评估使用九维 Rubric 和五档锚点，模型负责给出维度判断与引用，服务端回填权重、计算总分、钳制分数区间并验证引用来源。是否修订由确定性规则决定，例如总分、严重问题和合规维度；需修订时选择最低分集，生成完整新稿，连续性检查通过后再重评。修订最多一轮，若分数明显下降则转人工复核。

### 继续追问速答

- **为什么不能只看总 accuracy？** 高风险的错误目标或误执行可能被多数类掩盖，需要按类别和损失拆指标。
- **如何做 bad case 闭环？** 保存输入、版本、ContextManifest、检索 trace、模型输出和失败分类；归因后新增最小回归样本，再决定改 Prompt、数据、检索还是控制逻辑。
- **Agent 完成率是多少？** 先追问分母。当前可报告确定性规则和 FakeLLM E2E，不能说成真实模型联合成功率或用户采纳率。

### 证据与红线

- [Agent 评测报告](AGENT_EVAL_REPORT.md)、[评测矩阵](EVALUATION_MATRIX.md)。
- 360 条是评测资产规模；Prompt v1.4 真实模型联合结果尚未执行。

## M13｜模型、Prompt 和结构化输出怎样选型与兜底？【B】

### 典型问法

- 底层用什么模型，为什么这样选？
- 大小模型是否做动态路由？
- Prompt 怎样约束输出，JSON 不合法怎么办？
- 模型幻觉、流式 JSON 和输出被截断怎样处理？
- 模型说调用了工具，实际上没调用，怎么办？

### 参考回答

项目通过 `LLMClient.generate_structured` 抽象模型供应商，Skill 指定 Pydantic Schema。JSON 解析或 Schema 校验失败时，把具体错误反馈给模型做有限重试；`finish_reason=length` 不做相同请求的盲目重试，而是调整预算或拆分任务。权限、分数、目标版本和工具执行结果不从自然语言自报中读取，而由服务端事实验证。

当前没有完成基于任务难度的大小模型动态路由，所以我会把它作为优化方案而不是现状。若要实现，会先按任务类型、质量门槛、上下文长度和成本建立离线矩阵，再让简单分类使用轻模型、创作和复杂评审使用强模型，并保留回退与版本化评测。

### 继续追问速答

- **JSON mode、Schema、Pydantic 有何区别？** JSON mode 保证大致语法；Schema 约束结构；Pydantic 在服务端做最终类型和业务前置校验，三者都不替代授权。
- **如何降低幻觉？** 明确事实来源、RAG、结构化输出、引用验证、确定性工具检查和人工门；不存在单一“消除幻觉”方案。
- **是否自己部署模型？** 当前主要使用兼容外部 API；不要虚构 vLLM/CUDA 部署经验。

## M14｜Tool、Skill、MCP 和多 Agent 分别是什么？【B】

### 典型问法

- MCP、Function Calling、Tool 和 Skill 有什么区别？
- Skill 为什么不是脚本或 Workflow？
- 多 Agent 之间如何路由、通信和共享上下文？
- Skill 能否自动沉淀，怎样防止错误 Skill 污染？
- MCP Server 挂了是否影响主流程？

### 参考回答

我的划分是：Tool 负责可确定执行的动作，例如 Diff、统计、解析和导出；Skill 封装一次有领域输入输出的模型能力，例如 Writer、Evaluator 和 Planner；Workflow 负责状态和顺序。Function Calling 是模型表达调用意图的结构，MCP 是 Host/Client 与外部工具服务之间的发现和调用协议。

DramaAgent 当前支持可选的 MCP Tools 消费链路，工具要经过服务端目录、Schema、权限、确认和结果限制；外部 MCP 故障只局部降级，核心创作不受影响。项目不提供 MCP Server，也不支持自主多工具循环。对于“自动沉淀 Skill”，当前没有实现；合理方案是把轨迹先生成候选 Skill，经离线回放、安全扫描、版本化和人工审批后发布，不能让一次成功轨迹直接进入生产工具库。

### 继续追问速答

- **多 Agent 如何通信？** 如果未来引入，应优先使用结构化任务、Artifact 引用和事件，不依赖自然语言互聊；还要定义冲突、超时和所有权。
- **Leader Agent 挂了怎么办？** 当前无 Leader Agent；若实现，应把任务状态放在持久层，通过租约重新选取协调者，而不是留在单进程内存。
- **MCP 与业务安全的关系？** MCP 统一协议，不负责项目权限、用户授权或幂等，这些仍由 Host 处理。

### 证据与红线

- [MCP 设计](MCP_DESIGN.md)、[扩展机制](EXTENSIONS.md)。
- 不要把“专业 Skill”说成多个自治 Agent。

## M15｜权限、安全、沙盒和 Prompt 注入怎样处理？【B】

### 典型问法

- Agent 权限怎么控制，怎样防跨项目数据泄漏？
- 上传文件和工具结果里有 Prompt 注入怎么办？
- 云端 Agent 如何做 workspace、memory 和目录隔离？
- 为什么需要沙盒，项目实现到什么程度？
- 密钥怎样避免暴露给模型？

### 参考回答

安全边界不能放在 Prompt 里。每个请求先经过身份和项目作用域校验；Artifact、上传文件、检索 chunk 和导出路径都绑定项目；RAG 在数据库查询层先过滤权限。Planner 只能提出白名单动作，服务端解析真实目标，写操作需要确认。外部工具描述、结果和用户文档统一视为不可信数据，用内容边界包裹，并限制长度和类型，不能自动触发下一次工具调用。

密钥只存在服务端配置和连接层，不进入模型上下文或日志；日志做脱敏，不记录完整 Prompt 和剧本。当前项目没有允许模型执行任意代码，因此不存在完整代码执行沙盒；现有“隔离”主要是项目归属、文件路径、工具 allowlist 和工作流权限。若增加 AI Coding，需要独立容器/微虚拟机、只读基础镜像、临时工作区、网络默认关闭、资源限额和执行后销毁，不能把现有路径校验说成完整沙盒。

### 继续追问速答

- **提示词分隔能完全防注入吗？** 不能，只是软防线；真正限制损害的是权限、工具白名单和服务端验证。
- **怎样测跨项目泄漏？** 建两个内容相似、名称相同的项目，覆盖检索、缓存、重试、导出和事件接口。
- **多租户现状？** 当前以项目作用域为主，不要把 MVP 说成成熟企业级多租户平台。

## M16｜失败、重试、降级和可观测性怎样设计？【A】

### 典型问法

- 模型、工具或节点失败时怎样重试？
- Agent 为什么失败，如何定位是哪一层的问题？
- Redis 丢消息、SSE 断线后用户还能看到进度吗？
- 如何防止 Agent 陷入循环或反复调用？
- 线上应该监控哪些指标？

### 参考回答

首先按错误是否可恢复分类：429、超时和部分 5xx 做限次指数退避并尊重 `Retry-After`；401、403、参数非法等直接失败；结构化输出错误由 Parser 带校验反馈有限重试；硬预算超限不重试。节点失败记录稳定 error_code，图的下游节点遇到 failed 状态会短路，避免原始错误被级联异常覆盖。

事件先写 PostgreSQL 并分配 sequence，再 best-effort 发布 Redis；SSE 使用 Last-Event-ID 从数据库补历史，同时有 Redis 实时通知和数据库轮询兜底。所以 Redis Pub/Sub 不承担可靠投递。排障时按 Turn → Action → Run → lease → node → LLM/tool → Artifact → event → SSE → UI 逐层检查，并关联 request_id、run_id 和错误码。

### 继续追问速答

- **监控什么？** 队列等待、节点耗时/失败率、重试、Token/调用数、模型延迟、检索命中、数据库连接与锁、SSE 活跃/重连、Run 卡住数量。
- **为什么记录轨迹？** 最终文本相似不代表过程正确；需要定位规划、上下文、检索、执行或评估错误。
- **Redis 全挂怎么办？** 实时性下降，但数据库事件和消息事实仍在，可轮询恢复。

## M17｜成本、延迟、吞吐和规模扩大怎样权衡？【B】

### 典型问法

- 每次任务多少 Token、多少模型调用，如何控制？
- Agent 响应慢，应该从哪里优化？
- 业务量增长十倍，哪个部分先成为瓶颈？
- 怎样定义 SLA、容量和降级策略？
- 模型成本、人工成本和效果怎么平衡？

### 参考回答

项目按 Run 记录调用次数和 Token，设置软上限告警与硬上限终止；上下文通过任务预算、摘要、RAG top-k 和正文分阶段控制。延迟不能只看模型，要拆成排队、数据库、检索、模型首 token、完整生成、校验和事件展示。优化前先用指标确认瓶颈，再决定减少上下文、并行无依赖步骤、换模型、缓存确定结果或扩 Worker。

流量增长十倍时，我会重点观察模型供应商限额、Worker 队列、数据库连接池和事件表，而不是默认 FastAPI async 能无限并发。当前单项目限制一个活动 Run，优先保证版本一致性；若要提高吞吐，可按项目并行、为模型调用设置全局/租户信号量，并对非关键 RAG、语义评估设计显式降级。项目没有真实生产 SLA 或海量 QPS 数据，因此应回答容量规划方法，不虚构数字。

### 继续追问速答

- **软/硬预算区别？** 软上限只告警；硬上限在真实调用前拒绝继续，给成本确定上界。
- **哪些结果可以缓存？** 确定版本、固定 Prompt/模型配置下的纯派生结果；创作请求不能仅按文本随意共享。
- **SLA 如何定？** 按任务分层：交互规划秒级，长任务用排队时间、阶段进度和最终完成时间；同时定义错误预算和降级行为。

## M18｜为什么做云端 Agent？并发修改和工作区隔离怎么处理？【B】

### 典型问法

- 为什么做云端服务，不做本地 CLI/Harness？
- 多个用户或 Agent 同时修改同一作品怎么办？
- workspace、memory 和文档怎样隔离？
- 云端状态丢失、连接断开怎样处理？
- 如果改造成 Coding Agent，架构哪些地方要变化？

### 参考回答

DramaAgent 选择服务端形态，是因为作品要跨会话保存、分阶段审阅、在浏览器展示进度和版本，并支持任务在用户断开连接后继续执行。云端的代价是权限、租约、持久化、成本和隔离必须显式解决；本地 CLI 在代码仓访问、隐私和低延迟上更有优势，两者并非谁一定更先进。

当前系统按 project_id 隔离 Artifact、消息、检索和事件，一个项目同时只允许一个 queued/running Run，写操作绑定源版本并在确认时检查 stale，因此不会让两个 Agent 静默覆盖同一稿件。若扩展为 Coding Agent，仅靠 Artifact 版本不够，还要使用独立工作树/容器、文件锁或变更集、三方合并、测试门禁和受限网络；这是迁移设计，不是当前已经具备的能力。

### 继续追问速答

- **用户断线任务会停吗？** 不会；Run 在服务端执行，重连后按事件 sequence 补进度。
- **为什么限制单项目一个活动 Run？** 先保证作品版本和用户心智一致，牺牲同项目写吞吐。
- **多 Agent 并行何时可行？** 修改范围可隔离、合并规则明确、验证可自动化时，例如不同独立分支，不是直接共写同一文件。

## M19｜如何保证 AI 生成内容/代码的质量？DDD、SDD、TDD、CI 怎样落地？【B】

### 典型问法

- AI 生成的结果怎么审查，怎样避免偏离设计？
- TDD/SDD/BDD 在 Agent 项目里有什么价值？
- 测试应该在哪个门禁阶段介入？
- 为什么 AI 时代反而更需要领域边界和分层？
- 项目如何接入 CI/CD，测试会不会拖慢交付？

### 参考回答

AI 能提高生成速度，但不会自动提高需求正确性，因此我把规格、验证和证据放在生成之前。DramaAgent 以 DEV_PLAN 的验收条件和领域语言约束任务，先为状态、幂等、权限和失败语义写测试，再实现节点和服务；Prompt 输出要经过 Schema、领域校验、确定性规则和端到端回归。CI 分层运行 Ruff、mypy、pytest、Vitest 和必要的 Playwright，真实模型评测单独显式触发，避免把昂贵且波动的调用混进普通单测。

DDD 在这里不是为了套目录名，而是区分 Turn、Action、Run、Artifact、Story State 等具有不同生命周期的概念，让 AI 生成代码时不能把“聊天记录”“执行状态”和“作品事实”混成一张表。SDD 用规格和验收条件约束生成方向，TDD 用可执行测试锁定行为，BDD 可用于描述用户可见的确认和恢复场景。测试分层可以让快速单测先挡住大部分错误，再运行集成和 E2E，不必每次都跑真实模型。

### 继续追问速答

- **如何评审 AI 代码？** 看是否满足规格、领域边界、权限、异常路径、事务范围、并发语义和测试，而不只看能否运行。
- **项目是不是完整严格 DDD？** 借鉴领域建模和分层，但不要宣称完成了完整战略 DDD、限界上下文治理。
- **测试数字说明什么？** 说明工程合同在 FakeLLM 环境中稳定，不说明真实模型内容质量。

## M20｜你的个人贡献、最大难点、失败案例和下一步是什么？【A】

### 典型问法

- 你主导了什么，哪些部分是你亲自完成的？
- 项目最大的工程挑战是什么？
- 讲一个真实故障或错误决策，怎么定位和修复？
- 如果重新做一次，最想重构哪里？
- 再给两周时间，你会优先做什么？

### 参考回答

这道题必须按真实经历修改，不能照抄“我主导”。一个安全的回答结构是：我负责了哪一条完整链路、做了什么关键取舍、用什么代码或测试证明、还有什么没验证。例如可以选择“长任务恢复”作为主线：我把 API 接收、数据库 Run、租约领取、LangGraph checkpoint、Artifact 幂等和 SSE 补发串成一条链，关键取舍是 PostgreSQL 作为事实源，Redis 只做加速，并明确 checkpoint 不能保证模型 exactly-once。

故障故事可以使用项目里真实记录过的案例：LangGraph 静态边不会因为 State 标记 failed 自动停止，导致下游继续执行并覆盖原始错误。定位后在每个节点入口增加 failed 短路守卫，并通过错误码回归测试验证。这个故事能说明我不是只会画架构图，而是理解框架语义、失败传播和测试证据。

如果再给两周，我会优先跑当前 Prompt v1.4 / dataset v4 的真实模型评测，并对 RAG 与 Memory 做冻结输入消融和人工复核。原因是工程链路已有较强确定性测试，而最大的不确定性已经转移到真实模型质量和用户价值；继续堆新 Agent 角色不如先补证据缺口。

### 继续追问速答

- **最大的技术取舍？** 模型负责理解和生成，服务端掌握执行、版本、预算和终态；牺牲部分自由度换可恢复和可审计。
- **最想重做哪里？** 可以答统一评测证据包或更清晰的派生状态失效机制，但要结合自己真正理解的代码。
- **怎样证明个人贡献？** 准备 2～3 个具体文件、测试名称、故障记录和设计决策，而不是只列框架。
