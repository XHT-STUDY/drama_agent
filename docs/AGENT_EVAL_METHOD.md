## 0. 一句话总纲

> **Agent 评估没有单一指标能解决，我的做法是把评估对象拆成"行为"和"产物"两个，各自沿 EDD
> 生命周期组织：上线前用组件评测→集成评测→发布闸门回答"能不能上"，上线后把同一组指标搬到
> 真实流量持续监控；能用代码断言的绝不调模型，必须用模型的按"零成本契约级 / 真实模型级"
> 两级分离，没跑的不写数。**

三个记忆锚点：

| 锚点 | 内容 |
| --- | --- |
| **双对象** | 评**行为**（听懂没→做没做对→办成没）+ 评**产物**（剧本好不好卖座）——两套独立资产 |
| **一条主线** | EDD：先定义"怎么算成功"再动手；选型期→开发期→发布期→运行期四个目的串成生命周期 |
| **两级纪律** | 第一级进 `make test`：FakeLLM + 确定性规则，零模型调用；第二级 `eval_real` 显式 marker：真模型，不进每次提交 |

## 1. 为什么必须区别于传统测试（理论地基，30 秒）

传统测试断言 `输出 == 期望值`，Agent 打破了它的全部前提：

1. **非确定性**：同一输入两次运行结果不同，"通过/失败"判定失效；
2. **开放式任务**：正确答案无法枚举，只能打分/相似度/通过率去度量"好不好"；
3. **评测对象是轨迹不是返回值**：规划→调工具→观察→再规划；
4. **失败形态不同**：不是抛异常，而是选错工具、目标跑偏、**自以为完成**、绕圈子；
5. **裁判本身有偏见**：LLM-as-a-judge 有自我偏好/首位偏差/冗长偏差，且"偏好 ≠ 正确"。

所以方法论的核心结论：**评估必须前置为开发范式本身（TDD→EDD），并且确定性手段优先、
模型裁判被确定性校验包围。** 这两条在本仓库不是口号，是结构（见 §2/§4）。

## 2. 双对象：评什么

| 对象 | 问题链 | 本仓库资产 | 状态 |
| --- | --- | --- | --- |
| **A. Agent 行为** | 听懂没（意图/澄清）→ 做没做对（计划合法性/确认门/幂等）→ 办成没（goal_status + 证据） | `backend/tests/evals/agent_commands.json`、`agent_outcomes.json` + 两个 eval harness + `tests/integration/api/test_agent_turns.py` 等契约测试 | ✅ 已落地 |
| **B. 产物质量** | 这集剧本抓不抓人、爽不爽、合规吗 | Rubric v2 评分矩阵（9 维 × 5 档锚点 + 分带 + 信号 + 证据溯源）+ 确定性修订门 | ✅ 已落地 |

拆成两个对象的价值：**行为用"功能正确性"就能测**（意图对不对是可以标注的标准答案），
**产物只能"LLM-judge + 确定性校验"混合测**——武器库选型口诀（§3）在两个对象上自然分工。

## 3. 武器库选型：一个口诀管到底

> **能用功能正确性就别用相似度，能用相似度就别用 LLM-judge；用 LLM-judge 的地方必须被
> 确定性校验包围。**

| 档位 | 方法 | 在本仓库的落点 |
| --- | --- | --- |
| 最客观 | 功能正确性（可程序化验证） | turn_type/intent/target/batch 联合契约评测（240 开发 + 120 盲测 = 360 条，dataset v4）；澄清召回（14 条确定性歧义用例）；goal_status 与确定性证据的一致率；preflight 澄清"调用即失败"的 LLM 桩证明 |
| 中间 | 相似度/连续分 | 评估器证据引用与剧本原文的归一化匹配（命中→`verified=true`）；（检索 golden set 的 recall@5 已设计未跑） |
| 最主观 | LLM-as-a-judge | Rubric v2 九维打分——但它被四道确定性围栏包围（§5） |

GPT-4 裁判与人类一致性 85%、高于人类之间的 81%（AI Engineering）——这是"敢用 judge"的依据；
"裁判有偏见"是"必须加围栏"的依据。两句一起说，才是完整态度。

## 4. 生命周期主线：每个阶段测什么（对应通用框架 3.2/3.3）

### 4.1 选型期：硬约束初筛 + 私有集终筛

- 硬约束先行：function-calling 支持是硬门槛；成本/延迟/隐私划掉一批候选。
- 终筛不看公开榜单（数据污染），用**业务私有数据集盲测**：真实模型评测 harness
  （`EVAL_LLM_ENABLED=1`，provider/model 显式注入）就是这条的载体；报告带模型名 +
  prompt 版本落 eval 文档。
- 状态：harness ✅；系统性的多模型横评**未做**（单 provider 部署，无疼点）——诚实说法是
  "选型的**评测基础设施**已建成，横评随第二 provider 接入即可跑"。

### 4.2 开发期 · 组件级评测（测零件）

| 零件 | 对应通用框架 | 本仓库做法 | 状态 |
| --- | --- | --- | --- |
| **Planner（=工具选择+规划）** | 工具调用评测 + 规划评测 | 动作空间刻意封闭：6 个白名单意图（含 continue）+ 服务端模板化计划。评测集 = 用户话语→turn_type/intent/target/batch 联合契约（360 条含 120 盲测，dataset v4），真实模型分意图报 micro/macro P/R/F1 + 目标/批次准确率，并按发布门槛判定；规划合法性由结构兜底（意图外工具名/ID 直接 422，**不是靠测出来而是靠设计消除**） | ✅ 已跑过 v1.3 基线（create_script F1 96.8%，60/60 可解析 0 截断；已归档）；v1.4 契约评测待跑 |
| **澄清（preflight）** | 规划失败之"该不该做" | 12 条确定性歧义/越界/冲突用例，FakeLLM"调用即失败"证明澄清**零模型调用**完成，召回 100%；真实模型澄清召回 87.5%（1 漏 1 误） | ✅ 两级都有数 |
| **评估器 Prompt** | Prompt 评测 | Prompt 版本化（evaluate_episode v1.2）+ 契约哈希快照进 CI + golden fixture（含跨场漂移/无法溯源/分带越界三个分支样本） | ✅ |
| **RAG 检索** | 检索评测 | 两级纪律照抄意图评测：一级 FakeEmbedder+fixture 测管线不回归（路由缺口/过滤/去重）；二级真 embedding + golden set，recall@5 门禁，挂夜间/发版前 | ⚠️ 已设计未跑（诚实认领） |

组件评测的关键取舍要讲出来：**能写规则的先写规则**——规划合法性用白名单+目标选择器消除一整类
失败，评测资源只花在真正需要模型判断的地方（自然语言→意图的映射）。

### 4.3 开发期 · 集成级评测（测整机）

| 通用框架 | 本仓库做法 | 状态 |
| --- | --- | --- |
| **任务结果评测**（目的决定严格度：排名要严/诊断要细/监控要连续） | `agent_outcomes.json`（32 条）：Run 终态 + 证据 → goal_status（achieved/partially_achieved/blocked）+ 后续建议。确定性规则版 CI 一致率 100%（26 条）；语义版 harness 就绪、**人工基准未标，未跑**。严格度选择：判断"办成没"用确定性证据优先（artifact 存在性/版本号），不靠模型自觉 | CI ✅ / 语义 ⚠️ |
| **多轮交互评测**（用户模拟器 + 终态+Rubric 判分思想） | 无独立用户模拟器；用 **E2E 场景覆盖多轮结构**：模糊修改→澄清无 Run、重复发送不重复消息、第 3 集修订→版本 Diff、部分达成→一次后续计划→再确认、刷新恢复。`make e2e REPEAT=5`：7 用例 × 5 轮全过 | ✅ |
| **轨迹/过程评测** | 轨迹被架构确定性化：执行路径是服务端模板（不是模型现场规划），所以"轨迹对不对"转化为**契约测试**：Turn 幂等收据、并发确认单活跃 Run、PG 租约接管、checkpoint 恢复不重调已完成节点 | ✅ |
| **多 Agent 协作评测** | **不适用，且是决策不是缺失**：封闭动作空间 × 高错误代价 × 有确定性验证器 × 路径可枚举——四变量全指向单编排器。自主性预算花在理解用户，不花在选工具。若面试官追问开放域：`explain` 只读意图是有界 ReAct 沙箱，演进时先装进只读盒子再扩权 | 决策 ✅ |

### 4.4 发布期 · 评测集 + Pipeline + 发布闸门

组装顺序遵守"**指标先行，数据才有依据**"：先定各维怎么测 → 据此标注评测集（单测粒度
`test file` / 回归粒度 `evalset`）→ 绑定业务指标 → 设闸门。

`make ci` 闸门清单（每次提交全过）：

| 维度 | 闸门 |
| --- | --- |
| 代码质量 | Ruff + ESLint + mypy(322 files) + tsc 零错误 |
| 测试 | 后端 1099 passed / 前端 219 passed；覆盖率门禁 总体 ≥75%、核心 domain/workflows/artifacts ≥85% |
| 契约评测 | 评测集规模契约（commands ≥50 / outcomes ≥30）、五类 intent 覆盖、preflight 澄清召回、Outcome 确定性规则一致率 |
| E2E | Playwright 全链路，发版前 `REPEAT=5` 连续 5 轮 |
| **产物质量闸门** | Rubric need_revision 确定性规则：维度分 <75（修订阈值与 4 档下界对齐）→ 自动进修订循环（`max_revision_rounds=1`）→ 连续性检查 → 重评 |
| **成本闸门** | per-run 调用数 18（软）/24（硬）+ 200,000 token 硬顶，`check_budget` 超限熔断；llm_calls 全量审计 |

要点：**75 分这道门是产品语义的闸门，不是模型说了算的**——分数可从档位推出（分带 clamp）、
修订触发是确定性规则，主观部分被证据包围。

### 4.5 运行期 · 上线后监控

- ✅ 已落地：Prometheus `/metrics`、Run 诊断接口、llm_calls 审计计费、SSE 进度、全链路
  `error_code` 归因（失败可归因到层）。
- ⚠️ 认领的 gap：输入/输出分布漂移检测、A/B 灰度框架、guardrail 触发率面板——单租户本地

## 5. LLM-as-a-judge 偏差治理（Rubric v2 的存在理由）

五困境 → 五道对策（这是"产物评估"最出彩的部分）：

| 困境 | 对策 | 落点 |
| --- | --- | --- |
| 非确定性→分数漂移 | 先定档再给分：9 维 × 5 档锚点 + 分带 clamp（档位是语义判断，冲突时语义赢；clamp 后才进加权总分） | `knowledge/rubric/mvp_v2.yaml` + `clamp_score_to_band` |
| 证据幻觉 | 每维 evidence 必须逐字引用原文，服务端归一化溯源：命中→verified、跨场→自动纠正、找不到→`verified=false` 前端琥珀标注，**不伪装** | `EvaluationSkill._normalize_assessments` |
| 标准漂移 | Rubric 是数据不是 prompt 散文：yaml 版本化（v2.0.0）+ `ensure_weights_match_enums` 双处一致性校验 + 契约哈希测试 | rubric.py / manifest.yaml |
| 数据污染 | 评测集全部自建（60 + 32 条，覆盖五类意图/三种 goal_status/边界与越界），不用公开 benchmark 排名 | tests/evals/ |
| 裁判偏差 | 已认领未跑的三个实验：①方差测量（10 集×5 次，报 75 分带翻转率+temp=0 对照，≈50 次调用）②评估器换异家族（配置一行，断开 self-preference 结构相关）③残差配对测量 E[ΔA−ΔB] | 见 MOCK_INTERVIEW_SESSION 附录 B |

残余风险如实说：评估 temperature 0.3 是判断不是测量；75±4 噪声带与短剧实际质量分布（70 上下）
重叠，冤假修订烧掉的是**全场唯一的自动修订名额**（`max_revision_rounds=1`）——这就是为什么
方差实验排位很高。

## 6. 面试交付脚本

### 6.1 60 秒版

> 我的项目评估分两个对象：**行为**和**产物**。行为是"听懂没、做没做对、办成没"——我建了
> 360 条命令评测集（240 开发 + 120 盲测）和 32 条结果评测集，两级纪律：FakeLLM 契约评测进 make test 零模型调用，
> 真实模型评测显式 marker 不进每次提交，真实跑过意图 P/R/F1，主路径 F1 96.8%。产物是剧本
> 质量——LLM-judge 免不了，但我用 9 维 5 档锚点先定档再给分、分带 clamp、证据逐字溯源服务端
> 校验、修订触发是确定性规则，把裁判的不确定性压到只剩语义判断本身。整条链沿 EDD 生命周期：
> 上线前发布闸门（一千多个测试 + 契约评测 + E2E 五轮 + 成本预算熔断 + 75 分修订门），上线后
> 同一组指标搬进 Prometheus 和 Run 诊断持续盯，线上样本回灌评测集。纪律一句话：**没跑的
> 不写数**。

### 6.2 预案追问（5 条最可能的）

1. **"75 分门禁的方差多大？凭什么信？"** → 如实答：没测过，这是第一优先实验（50 次调用
   报翻转率）；先给算术——若总分 σ≈4，71~79 带内误判概率约三成，代价是唯一修订名额的
   机会成本，所以锚点/clamp/溯源先上（结构性降压），数值测量紧随。
2. **"为什么没有轨迹评测/Pass^k？"** → 轨迹被架构确定性化了：执行路径是服务端模板不是模型
   现场规划，轨迹正确性转化为契约测试（幂等/租约/checkpoint），可以代码断言就不需要
   轨迹打分；Pass^k 服务排名场景，我的场景是诊断与门禁，rubric+契约更合适——目的决定方法。
3. **"多 Agent 协作怎么评？"** → 先讲为什么单编排器（四变量决策），再给演进路径（只读沙箱
   先行）；如果真上多 Agent，交接链比对 + 消融实验 + 质检 Agent 三件套是现成答案。
4. **"和 RAGAS 什么关系？"** → RAGAS 是组件级（检索/生成）评估的事后测量；我的体系在它
   之上还有行为层（意图/结果）与闸门层；检索侧 recall@5 golden set 已按两级纪律设计（认领未跑）。
5. **"评估体系最大的短板？"** → 诚实三连：评估方差没测、评估器同家族、检索评测没跑——
   然后立刻接"打破循环的顺序和成本"（50 次调用/一行配置/一天 harness）。
