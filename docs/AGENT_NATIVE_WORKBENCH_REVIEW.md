# DramaAgent：面向个人创作者的持续共创工作台

日期：2026-09-12。状态：方案建议，尚未实施。

后续：[分阶段实施方案](/Users/kennywu/Documents/3-VibeProject/product/drama_agent/docs/AGENT_NATIVE_IMPLEMENTATION_PLAN.md)已细化为 26 张任务卡，实施范围与排期以该方案为准。

本轮目标：从短剧创作的实际任务出发，评估整体产品与架构如何优化。用户已确认优先场景为“个人创作者与 AI 持续共创”，允许重新设计整体架构。

证据范围：当前仓库设计、实现、测试用例及保存的评测结果，以及官方框架文档和实现。本轮未安装运行依赖、未运行应用或测试、未调用真实模型。代码路径分析不等于已复现运行故障；保存的评测结果不等于当前模型基线。

## 1. 推荐方向

**把 DramaAgent 做成以作品为中心、由一个 Agent 持续协作的短剧创作工作台。保留技术栈，重构创作任务、作品版本和验收证据之间的关系。**

创作者真正要完成的事情包括：找到值得写的故事方向、确定人物和节奏、写出可判断的样稿、在具体场景上反复修改、保持多集连贯、交付自己认可的版本。工作台应减少这条路径上的重复描述、页面切换、误改和无效等待。

这里的 agent-native 应体现为五种可观察行为：

1. 知道用户此刻在看哪一稿、哪一场，能按需读取正文与相关事实。
2. 记住一个持续的创作目标，能依据实际结果选择下一步。
3. 在已经授权的范围内完成必要检查和修改，不把内部步骤逐项交给用户调度。
4. 保留作者的控制权：随时补充意见、暂停、亲自编辑、比较和采用。
5. 能说明改了什么、依据什么、哪些要求仍无法确认。

最小方案是把现有正文、评估、Diff 和聊天整合到一个工作台，并打通阅读上下文。推荐进一步完成候选稿与采用稿、局部修改和剧情状态，再扩展自主执行。直接更换 Agent 框架，无法解决作品基线和验收证据的问题。

## 3. 工作台应该如何组织

### 3.1 作品为中心的三个区域

```text
┌─────────────────────────────────────────────────────────────┐
│ 项目 / 当前创作目标                 任务状态 · 暂停 · 导出     │
├────────────┬────────────────────────────┬───────────────────┤
│ 作品导航    │ 作品画布                    │ Agent 共创        │
│            │                            │                   │
│ 故事设定    │ 第 3 集 · 当前采用 v2        │ 当前目标           │
│ 分集大纲    │                            │ 已完成 / 待判断    │
│ 剧集 / 场景 │ 正文、场景、台词             │                   │
│ 参考资料    │ 选中 → 解释 / 修改 / 固定设定 │ 对话与修改意见     │
│            │                            │                   │
│ 待审稿件    │ 查看候选 v3 / 差异 / 采用    │ 修改范围与预算     │
└────────────┴────────────────────────────┴───────────────────┘
```

正文占据主要空间。检查与 Diff 根据当前任务展开，不要求永久四栏。窄屏优先保证正文阅读，对话通过抽屉或切换显示，保留位置与草稿。键盘选择、焦点返回、状态朗读和对比高亮的非颜色提示属于基本验收。

第一步直接复用 ScriptView、StoryBibleView、OutlineListView、EvaluationPanel、DiffView。局部编辑先采用场景与台词字段编辑，不必先引入通用富文本框架。

当前目标应成为稳定的工作台区域，不再从“最后一张计划卡”推断正在做什么。主界面只需告诉作者：正在改哪一稿、完成了哪些内容、下一件需要他决定的事是什么。技术节点、原始事件和完整调用记录放在可展开的运行详情。

### 3.2 新项目默认先验证方向，再扩写

推荐路径：

想法或素材 → 整理创作约定 → 查看并调整设定 → 形成大纲 → 写一集样稿 → 调整人物声音与节奏 → 按小批次续写 → 交付采用稿。

“创作约定”只包含对当前项目有用的信息，例如受众、题材、目标集数、单集时长、核心冲突、语气与不能改动的设定。缺信息时优先提出一个影响方向最大的具体问题，能使用合理默认的内容先给可修改草案。

这是首次创作的推荐顺序，不是所有用户必须走完的向导：导入已有原稿可以直接修改；作者要求“先试写一场”时允许探索稿，之后再整理设定。已有 Phase L 保持需求、设定、大纲、正文的依赖顺序；需要补齐的是设定自身的审阅与修订入口，以及默认先一集样稿的产品选择。

### 3.3 修改发生在作品上

用户选中第三场，说“冲突提前，但保留最后一句台词”。系统自动携带稿件版本、场景及选区，展示“本次只改第三场”的范围标签。用户能查看为什么要改、直接编辑、继续提出意见，也能恢复旧稿。

明确写出“修改第 3 集剧本”时，不必先手选目标。若用户当前看第 2 集，却明确要求修改第 3 集，应以明确指令为准并显示目标；若选区、文本和任务范围互相冲突，则询问一次。

### 3.4 候选、采用与授权分开

| 行为 | 默认规则 |
|---|---|
| 讨论方向、解释正文、检查问题 | 直接进行；消耗计入任务预算。 |
| 用户要求“改好这一场” | 视为授权在该场生成候选稿并完成必要检查；不逐次确认内部动作。 |
| 本次改稿产生多个内部候选 | 展示最终候选及必要比较，审核一次即可。 |
| 改已锁定设定、扩大到其他集、突破预算 | 说明新增范围与影响，获得新的授权。 |
| 将候选设为后续创作基线 | 作者采用，或作者明确授权“采用后继续”。 |

只有设定、大纲、正文等创作内容进入候选流程；评分、诊断和检索记录是证据，无需逐项“采用”。

作者授权续写三集时，这三集可以在任务内部引用前一集候选稿，最后作为有依赖关系的候选包审阅。项目采用稿保持不变。部分采用时校验依赖，不能让依赖未采用剧情的后集悄悄进入正式基线。

继续讨论某份候选稿时，保留该候选的活动上下文；“我还想改这里”不会自动切回采用稿，也不隐式采用这份候选。

## 4. 推荐架构：单一编排器、持久任务、专业能力

```text
                 工作台：作品 / 对话 / 审稿 / 交付
                                │
                    统一任务与作者决策入口
                                │
              创作 Task：目标、范围、授权、验收、预算
                                │
                 Agent：读取 → 判断 → 执行 → 检查
                      │                  │
                 上下文解析         受限专业操作
                      │          创作 / 局改 / 评估 / 导出
                      │                  │
                      │          既有 LangGraph Workflows
                      │                  │
       PostgreSQL：作品版本 / 采用指针 / Task / Run / Event
                      │                  │
                  按需检索          run_id 对应 checkpoint
                                         │
                                  SSE 更新工作台
```

这是模块化单体，继续使用 Next.js、FastAPI、Pydantic、PostgreSQL、pgvector、LangGraph 和已有 Redis。新增独立服务、运行语言、队列平台和向量数据库均为零。

### 4.1 将 AgentAction 演进为创作 Task

Task 对用户表达“一件持续的创作工作”，例如“把第三集改到女主主动推动冲突，同时保留身份悬念”。

不再额外叠加 Task → Action → Run 三套执行状态。推荐将现有 AgentAction 演进为 Task，迁移期可沿用物理表；AgentTurn 保留为每次请求的幂等收据，Run 保存一段执行事实。

| 对象 | 负责什么 |
|---|---|
| Turn | 原始输入、幂等键、请求处理收据、关联 Task；多轮输入可指向同一任务。 |
| Task | 目标、约束、验收条件、作者授权、累计预算、任务修订号、待决策事项和候选工作版本。 |
| Run | 一段执行的类型、输入版本、Task 修订号、授权快照、结果与失败重试次数。 |
| Event / checkpoint | 段内工具调用、进度和恢复位置；首版不增加独立步骤表。 |

一个 Task 对应多个 Run。故障恢复继续使用原 Run 和 run_id checkpoint；作者决策后的下一段工作创建新 Run，通过明确的 Artifact 引用衔接。不要把所有 checkpoint 改为 task_id，也不要把旧 completed_nodes 拷贝进新批次。

Task 的“正在执行”尽量从其活动 Run 派生；“等待作者选择”和“目标是否完成”是业务状态。运行结束、质量检查不通过、等待采用和任务达成应能分别表达。等待作者的 Task 不占项目执行槽，允许作者在长任务暂停时单独修改大纲。

### 4.2 Agent 可选择动作，服务端限定能力和权限

先提供少量与作品直接相关的操作：读取作品片段、读取设定和剧情状态、检索资料、生成候选设定/大纲/正文、修改指定场景、检查约束、比较版本、生成导出物。专业生成操作继续复用既有 Skill/Workflow。

显式按钮直接调用同一应用服务，记录相同任务和授权信息，不必再调用模型猜测用户点击了什么。自由文本由 Agent 选择操作。两种入口共用项目归属、基版本、范围、预算和采用规则。

模型只提交业务目标和可验证参数。项目权限、存储路径、数据库会话、可执行能力集合由运行时注入。不要开放任意内部 API、SQL 或 shell。

现有 LLMClient 已提供 generate_structured。首版可以让它输出经过 Pydantic 校验的“下一操作或停止原因”，由服务端执行并把结果送入下一轮；不要求先加入新的 Agent SDK 或供应商原生 tool-call 协议。[现有接口](/Users/kennywu/Documents/3-VibeProject/product/drama_agent/backend/app/llm/protocol.py:25)

LangGraph 官方 ToolNode 已实现工具名校验、参数错误处理和运行时参数注入，这些边界可作为现有受限操作入口的参照；若后续使用原生工具调用，再复用该节点。项目授权与版本校验仍由领域操作负责。[官方实现](https://raw.githubusercontent.com/langchain-ai/langgraph/main/libs/prebuilt/langgraph/prebuilt/tool_node.py)

### 4.3 有界自主推进

每一步读取真实结果再决定：完成、继续修正、缺信息、需作者判断、预算不足。默认一次修订加必要检查；仅当发现明确可修复问题时，在原授权内允许一次纠错。提高九维总分本身不是继续循环的理由。

保留现有调用数和 token 限额作为初始保护值，改为任务累计且持久化。费用只有在有可信模型价格配置时才换算金额，否则显示调用/token消耗及上限，避免提供假精确报价。

运行期间的补充意见先保存为待应用的 Task 修订。到下个安全边界结束当前执行段，以新修订启动下一段；当前结果仍注明基于原要求。暂停与取消不承诺撤回已发出的模型请求，但必须阻止后续调用及未授权作品采用。

本方案将作者审稿与改变要求放在执行段之间：当前 Run 结束，Task 记录待决策事项；决定后以新 Run 携带作品引用继续。故障恢复才复用原 Run/checkpoint。LangGraph 原生 interrupt 支持图内暂停，但恢复会重入节点；本轮不把它与段间审稿混成第二套等待状态，也不另造通用暂停引擎。[官方中断文档](https://docs.langchain.com/oss/python/langgraph/interrupts)

### 4.4 先补齐现有恢复边界

以下是静态代码发现，应在扩大自主执行前以完整链路复现并修复：

- continue 新 Action 绑定原 Run，但 agent_actions.run_id 仍有唯一约束。现有测试中直接构造 gated Run 的路径不足以覆盖“聊天创建 → 暂停 → 聊天继续”。[约束](/Users/kennywu/Documents/3-VibeProject/product/drama_agent/backend/app/db/models/agent_action.py:24)、[续跑](/Users/kennywu/Documents/3-VibeProject/product/drama_agent/backend/app/application/agent_command_service.py:536)
- 正常续跑也增加 Run attempt_count，达到默认 3 次后进入耗尽分支；阶段推进应与故障重试分开。[领取逻辑](/Users/kennywu/Documents/3-VibeProject/product/drama_agent/backend/app/application/workflow_dispatcher.py:61)
- Dispatcher 依赖 startup/wake 的一次 drain，未见租约未来过期后的周期补扫；规划中 Turn 的重复请求也主要返回当前状态。[Dispatcher](/Users/kennywu/Documents/3-VibeProject/product/drama_agent/backend/app/application/workflow_dispatcher.py:237)
- 预算 begin 从零建立进程内记录，运行中取消使用内存标记；恢复后仍须保留任务预算和停止请求。[预算](/Users/kennywu/Documents/3-VibeProject/product/drama_agent/backend/app/llm/budget.py:99)、[取消](/Users/kennywu/Documents/3-VibeProject/product/drama_agent/backend/app/application/run_service.py:205)

数据库仍保持每项目最多一个 queued/running 执行槽。持久化预算需在调用前预留额度、返回后结算；调用结果未知时保留未结算额度，不能因超时当作零消耗。业务变更与 DB 事件在明确短事务中提交，再通知 SSE；不以消息推送成功与否决定作品是否保存。

## 5. 作品与上下文的数据设计

### 5.1 采用指针与局部修改

Artifact 的 draft/valid/invalid 继续表示内容合法性。增加按项目、作品类型、集数唯一的采用版本引用；生成新候选不移动它。采用时校验预期旧指针，处理用户手改与 Agent 完成同时发生的冲突。

每次执行段按 Task 修订号冻结实际使用的设定、大纲、正文、剧情状态、资料引用。任务内部另有候选工作版本集合，支持批内继续写作；项目默认上下文和导出仍读取采用集合。下一执行段可以采用作者新确认的版本，原执行段的快照保持不变。

在现有 JSONB 场景中增加稳定 scene_id，scene_number 只负责排序展示。首版文本选区使用基版本、scene_id、字段路径、选区原文及校验值；不必把每句台词拆成一张表。修改只返回允许范围的内容，由服务端合并成完整的新 Artifact，再沿用校验、Diff、导出。对原范围外的变化做确定性检查。

人工编辑与 Agent 编辑走同一个版本保存服务。插入新场景时分配新 ID，未改场景保留 ID。旧评估锚定旧稿；跨版本定位仅在有可靠场景对应关系时进行，不能猜测跳转。

### 5.2 先用好已有剧情状态

现有 ContinuityState 已有 character_id、loop_id、event_id，不需要重新发明人物图谱。优先接通已有 SummarizerSkill 对人物信息、关系、伏笔和时间线的更新。

剧情状态按实际稿件版本派生并保留来源。续写前加载前文状态；分批和重启不能只重建 StoryBible 初态然后跳过已写剧集。采用前文新稿后，使相关摘要和后续检查失效并重建；现有后集保留，标为需要复核，不自动整批重写。

模型推断的事实保持为提议。用户确认的设定、角色在某集知道的信息、给作者看的未来剧情应能区分，尤其要保护“作者知道真相，角色尚不知道”的边界。用户主动修改锁定事实时生成设定新版本并展示影响范围。

### 5.3 上下文采用索引加按需读取

先给 Agent 项目摘要与作品索引；解释或修改时读取目标正文及相关事实。保留 ContextBuilder 预算裁剪，用户要求、目标片段和锁定事实优先，缺关键内容时不能假装已经读过。

Deep Agents 的文件工具有按范围读取、结果长度限制和引用返回机制，值得借鉴的是“索引定位 → 按需读内容”的接口。DramaAgent 应将其映射为作品/场景读取，复用自己的 Artifact 存储，不需要接入整套文件 Agent。[官方实现](https://raw.githubusercontent.com/langchain-ai/deepagents/main/libs/deepagents/deepagents/middleware/filesystem.py)

RAG 用来补充具体创作问题，例如“这一场怎样设计身份误认”；人物已知信息和已采用剧情通过结构化查询获得。检索失败可降级，关键作品或已确认设定无法读取则暂停相关生成。知识库入口面向作者展示“参考资料、用途、本次采用的来源”，embedding 状态和检索试算保留在详情。

## 6. 把质量判断和运行状态分开

| 验收层 | 判断内容 | 判断方式 |
|---|---|---|
| 内容合法性 | Schema、角色引用、场景范围、版本归属、未授权变动 | 确定性代码。 |
| 目标约束 | 保留指定台词、不提前揭露秘密、修改位置与要求相符 | 能确定的直接检查；语义部分给具体文本证据。 |
| 剧作质量 | 人物是否可信、节奏是否更好、作品风格是否合适 | 现有评估辅助，作者采用或人工盲评作最终依据。 |

每条目标保存“满足 / 未满足 / 未验证”，并引用具体 Artifact 版本、场景和片段。没有证据、检查失败或模型不可用时，不能把未验证要求转成已达成。生成成功可以单独显示为“候选稿已完成”。

现有 Evaluator 已有原文引用溯源校验，应复用这一能力补齐 Outcome，而不是再增加一个常驻 Judge Agent。[评估实现](/Users/kennywu/Documents/3-VibeProject/product/drama_agent/backend/app/skills/evaluator.py:246)

结果卡默认显示三件事：具体改动、仍需作者判断的问题、查看候选稿。证据可展开并定位正文，不能为了缩短消息把未确认要求完全藏起来。

## 7. 渐进实施与验收

以下为一名熟悉仓库的全栈开发者的粗估，不是已验证排期；不含真实创作试用等待时间。整体涉及超过 8 个文件及跨层数据迁移，需要按阶段更新开发契约，每阶段独立可用。

| 阶段 | 可交付变化 | 主要复用与改动 | 验收 | 粗估 |
|---|---|---|---|---|
| 1. 同屏共创 | 正文与 Agent 同屏；阅读自动成为上下文；明确目标无需多余澄清；解释能读原文；结果如实区分已完成与未验证；导出固定版本。 | AgentWorkspace、ScriptView、现有详情组件、Planner/Context/Outcome、后端 ExportService。续跑静态风险先写最小复现并修正已有路径。 | 同一页面完成看稿→提出意见→查看修改；无正文证据不得宣称解决语义目标；历史导出不随新稿变化；聊天续跑超过三批可用。 | 5–8 人日 |
| 2. 作者控制版本 | 候选/采用指针、场景 ID、局部与人工编辑；基版本冲突检查；批内候选依赖。 | ArtifactService/Repository、domain/script、Reviser、Diff、选择上下文、导出选择器。 | 候选 v3 未采用时续写/导出仍基于 v2；只改第三场则其他场不变；部分采用检查依赖；并发修改不覆盖。 | 5–8 人日 |
| 3. 剧情连续共创 | 接通摘要与剧情状态；设定可修订并采用；按作品版本恢复；前文改变后显示下游影响。 | Summarizer、ContinuityManager、write_episode、ContextBuilder、StoryBible 视图与修订操作。 | 一次写五集和分批重启写五集，后续输入的前文状态一致；角色不会提前知道受保护秘密；旧摘要不会污染采用的新稿。 | 4–7 人日 |
| 4. 持久创作任务 | AgentAction 演进 Task；多执行段；按需操作与有界纠错；任务级预算、停止请求和输入修订；统一按钮与聊天入口。 | Turn/Action/Run 模型、AgentCommandService、Dispatcher、Lifecycle、SSE、现有工作流。 | 跨轮修改不丢目标；重启保留预算/取消；补充意见在明确边界生效；等待作者不占槽；越范围停下；完整任务可回放。 | 6–10 人日 |

第一阶段结束即有可用的改善，不依赖第四阶段。第二、三阶段让作品与记忆语义可靠后，再扩大自主执行。若只投入一轮开发，选择第一阶段，并将候选/采用语义列为下一优先级。

### 接口与迁移边界

- 扩展现有 Turn 请求：可选 task_id、活动稿件版本、scene_id 与选区锚点；幂等哈希纳入这些字段。
- 作者采用与编辑走同一作品应用服务，采用请求携带候选 ID 和预期旧采用版本；不接受客户端改写服务端计划。
- Task 查询返回目标、执行历史、候选版本、待决策项与累计消耗；继续、补充要求和停止使用同一任务入口。
- 新增 workflow_runs.task_id，保留旧 Action→Run 字段供旧执行路径读取；旧历史父子 Action 不强行合并。
- 新 Task 固定执行语义版本。旧 Run 和 checkpoint 按旧机制完成；新版任务的恢复不能交给旧后端解释。
- 旧项目首次迁移将迁移时的 latest valid 设为“沿用的当前稿”，记录其迁移来源，不伪称用户曾采用。历史 Artifact 内容、checksum 和版本号保持不变；旧稿缺 scene_id 时通过兼容读取，下一次编辑再产生新 schema 版本。

回滚首先关闭新任务入口，保留新版只读结果与作品数据。涉及采用语义后，不能只恢复旧前端并重新取 latest valid；兼容后端必须继续尊重采用指针。正在执行的新任务先在安全边界暂停或完成，保留可恢复数据，不做删表式回滚。

### 验证方法

工程门禁沿用 FakeLLM/FakeEmbedder、pytest、Vitest 和 Playwright。每阶段运行涉及路径的测试，再运行仓库 lint/typecheck/test；工作台变化补渲染与键盘流程验收。新增迁移必须验证旧数据可读、旧 Run 可恢复、新版本契约和回滚路径。

真实体验另用固定 20 个任务作为首批试用集：10 个局部改稿、5 个跨集续写、5 个候选采用与恢复任务。保持输入版本、模型与预算可比，记录作者采纳率、无关改动率、目标实际解决率、完成目标的耗时和成本。对主观质量采用匿名新旧稿比较，不用 Agent 自报分数替代人工判断。

硬约束验收要求未授权跨范围修改为零、历史版本改写为零、无证据却自报目标达成为零。主观质量和完成时间先建立现状基线，再判断新架构是否有实际增益。

## 8. 取舍与最脆弱的假设

**主要假设：有限范围的自主改稿能减少作者调度负担，而且不会降低作者对作品的控制。** 如果试用中候选采纳率低、无关变化多，优先改善上下文、局部工具和模型提示；保持单次改稿加人工判断，不增加循环深度。

不优先引入多 Agent 角色群聊、通用工作流搭建器、图数据库、微服务和完整 Git 分支系统。只有独立任务可以并行且评测证明收益时，再考虑内部委派；持续剧情写作暂保留顺序推进。

不把九维评分快速上涨当作品变好的充分证据。固定工作流适合可预测步骤，自主选择适合目标需要根据结果调整的部分；将两者组合，并通过实际任务衡量收益。[Anthropic 官方工程经验](https://www.anthropic.com/engineering/building-effective-agents)

个人创作者无需配置一组角色模型才能开始。产品层优先一个默认模型，角色模型覆盖放进高级设置；复用现有提供商接入。本方案没有新增第三方账号、MCP 服务或付费依赖。真实质量评测仍需要现有模型凭证和明确的测试预算。

这份建议会改变旧 DESIGN 中“每次写操作确认”“不修改 Story Bible”“最多一层后续计划”等限制。它们是此前阶段的范围决策；用户本轮允许整体重构，因此这里提出替代设计，实施前应将新阶段契约明确写入，保留旧任务兼容。PostgreSQL 事实源、不可变作品、Schema 校验、Fake CI 和服务端权限边界继续保留。[原设计约束](/Users/kennywu/Documents/3-VibeProject/product/drama_agent/DESIGN.md:45)
