# M1：项目价值、架构与个人贡献

## 母题

> DramaAgent 为什么存在，它比一次 Prompt 调用多解决了什么，整体如何运转，我实际负责什么？

## 回答卡骨架

- **核心结论**：这是面向长程、版本化内容生产的受约束 Agent 系统，不是一次性文本生成脚本。
- **核心链路**：自然语言请求 → 规划/澄清 → Action → 确认 → Run → 工作流 → Artifact → Outcome。
- **价值证据**：长程状态、写操作安全、失败恢复、版本追溯、评测修订闭环。
- **个人贡献**：只能讲自己能够打开代码、测试和日志解释的部分。
- **失败边界**：自动化测试、真实模型评测、业务效果不能混为一谈。

## 题目归属

- ★ **Q01** 请用两分钟介绍 DramaAgent，你解决了什么问题？
- ★ **Q02** 它是 Agent 还是固定 Workflow？
- ★ **Q04** 说出一条请求从输入到结果的完整控制链。
- **Q05** Turn、Action、Run、Artifact 分别解决什么问题？
- ★ **Q09** 这个项目最大的技术取舍是什么？
- **Q100** 如果面试官说“你的项目只是调 API”，怎么回应？
- **Q101** 你的方案比“一个 Prompt 直接生成剧本”有效多少？
- **Q105** 面试官要求你画一张架构图，应标哪些边界？
- ★ **Q106** 怎么解释你负责的部分与团队贡献？

## 练习顺序

1. 先练 Q01 的 90 秒版本。
2. 再练 Q04，把控制链说完整。
3. 用 Q02、Q09、Q100 练“为什么这样设计”。
4. 最后练 Q106，校准个人贡献边界。

# M2：Agent 自主性、规划与权限边界

## 母题

> 哪些事情需要模型判断，哪些事情不能授权给模型，为什么？

## 回答卡骨架

- **核心结论**：模型有建议权和生成能力，服务端拥有执行权、权限校验和最终状态判断权。
- **主要机制**：确定性 preflight、白名单意图、结构化选择器、服务端解析真实 ID、写操作确认、预算守卫。
- **取舍依据**：动作空间是否开放、错误是否可逆、路径是否可枚举、结果是否可验证。
- **失败边界**：Schema 只能约束形状，不能替代权限、版本和业务授权；提示词隔离不是安全边界。
- **演进方向**：先在只读、低代价、可回滚区域增加自主性。

## 题目归属

- ★ **Q03** 为什么选 Plan-and-Execute，而不是自由 ReAct 或多 Agent？
- ★ **Q10** 模型识别错意图会造成什么后果，如何降低风险？
- ★ **Q11** Planner 输出为什么不能包含任意工具名、Artifact ID 或 SQL？
- **Q12** 什么时候该澄清，什么时候该使用默认值？
- ★ **Q15** Function Calling、Tool Use、MCP 三者怎样区分？
- **Q16** Tool、Skill、Workflow 的边界是什么？
- ★ **Q17** Tool 返回的内容可能包含 Prompt 注入，怎么处理？
- **Q18** 如何设计一个安全的写工具？
- **Q19** 多 Agent 比单 Agent 一定更好吗？
- **Q20** 面试官要求当场为项目加一个“联网查题材热度”工具，你怎么设计？

## 练习顺序

1. 用 Q03 讲清自主性取舍框架。
2. 用 Q10、Q11 讲模型权限边界。
3. 用 Q15、Q16 建立工具概念。
4. 用 Q17、Q18 做安全追问。
5. 用 Q19、Q20 练迁移设计。

# M3：版本、幂等与并发一致性

## 母题

> 请求重试、并发提交或作品版本变化时，系统如何保证操作不会重复，并且一定作用于正确版本？

## 回答卡骨架

- **核心结论**：用户意图绑定确定版本；重复执行被幂等折叠；新的语义请求必须产生新版本。
- **主要机制**：不可变 Artifact、来源关系、input_hash、幂等键、唯一约束、源版本快照、stale Action。
- **数据库原则**：应用层检查改善体验，数据库约束保证最终正确性。
- **失败边界**：幂等键漏掉语义输入会吞掉新意图；把执行环境写入幂等键会失去重试去重能力。
- **关键区分**：意外重复由幂等处理；用户主动重写由版本模型处理。

## 题目归属

- **Q06** 为什么要把 LLM 调用放在数据库事务外？
- **Q07** 项目为什么将 PostgreSQL 设为事实源、Redis 设为加速层？
- ★ **Q08** 为什么 Artifact 不可变？版本和来源关系有什么用？
- ★ **Q13** 计划确认后用户又改了剧本，旧计划怎么办？
- ★ **Q14** 如何保证双击确认或请求重试不会执行两次？
- ★ **Q24** 为什么需要数据库唯一约束，应用层先检查不够吗？
- **Q25** “继续写下一批”怎样避免旧确认请求重放？
- **Q30** 如果用户修订第 2 集，第 3 集之后的剧情状态如何处理？
- **Q93** 为什么导出要冻结版本？

## 练习顺序

1. 先练 Q08，建立版本模型。
2. 再练 Q14、Q24，建立并发与幂等边界。
3. 用 Q13、Q25 处理陈旧请求。
4. 用 Q06、Q30、Q93 练事务和下游一致性。

# M4：长任务执行、恢复与事件交付

## 母题

> 当 Worker、进程、网络、Redis 或外部模型局部失败时，系统如何继续执行、避免扩大损失，并让用户看到真实进度？

## 回答卡骨架

- **核心结论**：执行是可重放的，持久化效果是幂等的，调用费用只能做到有界而非 exactly-once。
- **主要机制**：queued Run、数据库租约、心跳、checkpoint、completed state、有限重试、协作式取消、事件表、sequence、SSE 补发。
- **状态权威**：数据库记录真实效果；State/checkpoint 用于调度与恢复。
- **失败边界**：模型返回后、Artifact 落库前的崩溃仍可能导致重复调用；正在进行的第三方调用未必可以立即取消。
- **排障主线**：Action → Run → lease → node → event → SSE → UI。

## 题目归属

- ★ **Q21** 为什么用 LangGraph？状态里存什么？
- ★ **Q22** Checkpoint 能保证“模型只收费一次”吗？
- ★ **Q23** 数据库租约调度如何处理 Worker 崩溃？
- **Q26** 自动修订如何避免无限循环？
- **Q27** 取消任务时，正在进行的 LLM 请求会立刻停止吗？
- **Q28** 一集正文已保存，但剧情状态派生失败，怎么办？
- ★ **Q29** SSE 断线或 Redis 丢消息后，前端怎样追上进度？
- **Q84** LLM 请求失败时如何区分重试与立即失败？
- **Q89** PostgreSQL 的 `SKIP LOCKED` 有什么风险？
- **Q90** Redis Pub/Sub 能保证事件送达吗？
- ★ **Q95** 如何排查“用户确认了计划，但一直看不到结果”？

> 说明：Q26 同时与预算和 Outcome 有关，但主干仍是长任务退出条件，所以放在 M4。

## 练习顺序

1. 用 Q21 讲工作流状态。
2. 用 Q22、Q23 讲崩溃窗口与恢复。
3. 用 Q29、Q90 讲事件交付。
4. 用 Q27、Q84 讲取消与重试。
5. 用 Q95 串起完整排障链。

# M5：RAG 与知识检索

## 母题

> 如何让当前创作阶段拿到正确、相关、隔离且可追溯的知识，并单独证明检索质量？

## 回答卡骨架

- **核心结论**：RAG 是低权威增强信息，不是作品事实源，也不是幻觉或注入的自动解药。
- **完整链路**：摄取 → 切块 → embedding → pgvector → 元数据/项目过滤 → 排序去重 → 上下文预算 → trace。
- **选型依据**：先从实际失败样本判断需要 query 改写、混合检索还是 reranker。
- **评测原则**：检索和生成分开测；主看 recall@k、MRR、误召和下游证据使用。
- **失败边界**：检索内容可能错误、过期或恶意；项目隔离必须在查询层完成。

## 题目归属

- ★ **Q32** 说清项目的 RAG 全链路。
- **Q33** Chunk 太大或太小分别有什么问题？如何选大小？
- **Q34** Embedding 相似度高就代表内容对任务有帮助吗？
- **Q35** pgvector 里的精确检索、IVFFlat、HNSW 有何取舍？
- **Q36** 什么是混合检索和 RRF？本项目实现了吗？
- **Q37** Embedding、Reranker、LLM 生成器各做什么？
- **Q38** 什么是 HyDE？什么情况下不该用？
- **Q39** 为什么不把所有知识库资料一次性塞进 Prompt？
- ★ **Q40** 你怎样评估 RAG，不让生成质量掩盖检索问题？
- **Q41** 检索失败、向量库不可用时是继续还是中断？
- ★ **Q42** 用户上传的文档可能跨项目泄漏，怎么防？
- **Q43** RAG 能防 Prompt 注入或幻觉吗？

## 练习顺序

1. 用 Q32 画完整数据链。
2. 用 Q33～Q39 回答各阶段取舍。
3. 用 Q40 建立评测方案。
4. 用 Q41～Q43 讲降级、安全和能力边界。

# M6：Memory 与上下文工程

## 母题

> 如何区分对话记录、用户意图、项目事实、剧情状态和检索资料，并在有限上下文中保持长期一致性？

## 回答卡骨架

- **核心结论**：不同信息必须按来源、权威、版本和用途分层，不能都叫“记忆”。
- **主要对象**：原始消息、工作窗口、对话摘要、StoryBible、剧情状态、作品工作集、RAG 参考资料。
- **更新原则**：原始记录不可丢；摘要增量更新；结构化事实通过 typed delta 合并；冲突由权威和版本处理。
- **上下文原则**：按任务分配预算；当前目标正文不静默截断；记录 ContextManifest。
- **评测原则**：测召回、上下文到达和最终遵守，三者不能混成一个指标。

## 题目归属

- ★ **Q44** 对话历史、RAG 和 Memory 有什么区别？
- **Q45** 为什么“只保留最近 N 条消息”会失败？
- **Q46** 累计摘要如何更新，怎样避免重复和覆盖？
- **Q47** 长期记忆里出现过时或错误事实怎么办？
- **Q48** 角色“知道”和作者“计划让角色知道”有什么区别？
- **Q49** 为什么让 LLM 输出 typed delta，而不是直接覆盖整个连续性状态？
- ★ **Q50** ContextBuilder 怎样决定裁剪谁？
- **Q51** 为什么 ContextManifest 有价值？
- ★ **Q52** 如何证明 Memory 真的带来了收益？
- **Q53** Redis 短期窗口丢失会导致记忆丢失吗？
- **Q54** 多会话的项目级记忆怎样合并？
- **Q83** 长上下文模型能替代 Memory/RAG 吗？

## 练习顺序

1. 用 Q44 建立完整概念边界。
2. 用 Q45～Q49 讲写入和冲突。

# M7：Agent 评测与实验设计

## 母题

> 如何分别证明代码链路正确、模型行为稳定、业务判断有效，并诚实表达尚未证明的部分？

## 回答卡骨架

- **核心结论**：软件测试、模型离线评测和真实业务效果是三层证据，不能互相冒充。
- **指标原则**：根据错误代价选择 precision、recall、F1、最差轮次、成本和延迟，不能只看总 accuracy。
- **数据原则**：开发集与盲测集分开；版本绑定模型、Prompt、数据集和代码提交。
- **Judge 原则**：先测信度，再测效度；确定性部分由代码计算；引用必须回源；必要时人工对齐。
- **诚实边界**：没有跑真实模型就说“尚未执行”；FakeLLM 证明链路，不证明模型能力。

## 题目归属

- ★ **Q55** 软件测试与 Agent 评测有什么不同？
- **Q56** 如何评意图识别？为什么不能只报准确率？
- **Q57** 数据集怎样避免被 Prompt“偷看”？
- ★ **Q58** 360 条评测集是否意味着当前模型精度有保证？
- **Q59** LLM-as-a-judge 最大的风险是什么？
- **Q60** 项目如何避免“模型自报总分”？
- **Q61** 模型引用了剧本中不存在的一句话，怎么处理？
- **Q62** 为什么对创作质量不能只用 BLEU/ROUGE？
- **Q63** 如何设计一个有说服力的消融实验？
- **Q64** 线上 A/B 与离线评测分别解决什么问题？
- **Q65** 发布门槛应看平均值还是最差值？
- **Q66** 如果 Prompt 改进了创建意图，却使修订召回下降，怎么判断？
- ★ **Q67** 面试官问“你们的 Agent 完成率是多少”，怎么回答？
- **Q94** 该怎样测试一个 LLM 应用？

## 练习顺序

# M8：生产治理、安全、成本与扩展

## 母题

> 如何让一个概率系统在成本、延迟、权限、安全和容量上保持可控，并在异常时可定位？

## 回答卡骨架

- **核心结论**：概率输出之外必须有确定性的资源、权限和损害上界。
- **成本与延迟**：调用预算、Token 预算、超时、重试分类、队列等待、并发控制。
- **可观测性**：Run/节点/LLM/检索分层指标，轨迹、错误码、日志关联和诊断接口。
- **安全性**：身份与项目作用域、查询时权限过滤、输出脱敏、写操作确认、内容边界。
- **扩展原则**：先测队列、模型、数据库锁和连接池瓶颈，再决定扩 Worker 或改变语义。

## 题目归属

- **Q31** 如果业务量增长 10 倍，这个架构会先卡在哪里？
- ★ **Q85** 如何控制 Agent 的成本和延迟？
- **Q86** 线上 Agent 应监控哪些指标？
- **Q87** 为什么要记录轨迹，而不只看最终答案？
- **Q88** FastAPI 的 async 能让模型请求无限并发吗？
- **Q91** 如何防跨项目数据访问？
- **Q92** Prompt 注入与普通恶意输入的区别？项目边界在哪里？
- **Q103** 如果要把 DramaAgent 部署给多个团队，先改哪三件事？

> Q84 主归属 M4，因为它首先是失败分类与执行恢复问题；Q89、Q90 也主归属 M4。Q96 主归属 K2，因为它考查通用后端迁移能力。

## 练习顺序

1. 用 Q85 建立成本—延迟—质量三角。
2. 用 Q86、Q87 建立观测体系。
3. 用 Q91、Q92 建立安全边界。
4. 用 Q31、Q88、Q103 练扩展设计。

# M9：故障故事、反思与演进

## 母题

> 我亲自遇到过什么问题，如何找到根因，为什么原方案没有挡住，下一步如何用证据决定优先级？

## 回答卡骨架

- **故事结构**：预期 → 症状 → 排查 → 根因 → 修复 → 验证 → 遗留边界。
- **证据要求**：能指出代码、测试、日志或评测报告；不能只讲设计稿。
- **反思要求**：说明当时为什么做出那个判断，而不是事后把错误描述成显而易见。
- **优先级要求**：按业务损失、发生概率、可逆性、验证成本排序。
- **个人边界**：准确区分自己定位、实现、评审和验证的部分。

## 题目归属

- ★ **Q102** 讲一个你亲自定位的复杂故障。
- **Q104** 如果有两周时间继续改进，优先做什么？
- **Q107** 你最想重做项目的哪一处？

## 建议准备的两张故事卡

1. **实现缺陷故事**：例如幂等键、状态恢复、检索路由或版本一致性问题。
2. **证据不足故事**：例如真实模型评测、RAG 相关性或 LLM-as-judge 效度尚未完成。

不要为 Q102、Q104、Q107 分别背三份答案。一个真实故事可以自然产生“怎么修”“还缺什么”和“如果重做”的三个角度。

# 四、具体使用方式

## 第一轮：建立骨架

只练 30 道 `★` 锚点题。每道题完成：

```text
10 秒识别母题
60～90 秒首答
1 个项目证据
1 个设计取舍
1 个失败边界
```

## 第二轮：随机追问

每天选一个母题，从该母题的非星标题中随机抽五道。不得提前看答案，只允许看母题卡。

## 第三轮：跨母题组合

练习以下组合题：

- 模型规划错误 + Action 过期：M2 + M3
- Worker 崩溃 + 重复计费：M4 + M3
- RAG 命中错误 + Prompt 注入：M5 + M8
- Memory 召回成功但模型未遵守：M6 + M7
- 业务量增长 + 成本超限：M8 + M4
- 项目效果被质疑：M1 + M7 + M9

## 第四轮：真实面试迭代

每次面试后只更新母题卡，不新增完整答案。只有一个新问题无法被现有母题解释，并且类似问题累计出现三次，才考虑拆分或新增母题。

# 五、口径红线

1. 自动化测试使用 FakeLLM/FakeEmbedder，不能说成真实模型质量验证。
2. 当前 Prompt、数据集、模型版本必须绑定说明，历史实验不能冒充当前结果。
3. “效果幂等”不等于“模型调用 exactly-once”。
4. RAG、Memory、长上下文、微调解决的问题不同，不要互相替代式表述。
5. Schema 和结构化输出不等于业务授权与安全校验。
6. 没实现的 BM25、reranker、HyDE、多 Agent、后训练，只能讲判断依据和实验计划。
7. “我主导”“我实现”必须与真实贡献一致，并能给出代码或验证证据。
8. 没跑过的数据直接说没跑过，再说明如何验证；不要用设计目标充当结果。
