# 后端全链路详细日志增强方案

## 现状与根因

183 个后端文件中仅 53 个有日志；API 路由层、LLM 成功调用、Schema 校验重试、预算控制、异常处理器几乎无日志。更关键的是 `app/observability/tracing.py` 的 `push_request`/`push_run` **零调用**——run_id/node_name 从未进入日志，后台 Worker 日志无法按 Run 聚合。

## 改动清单（8 个部分）

### 1. 打通关联标识到日志格式（收益最大的基础设施）
- **`app/main.py`** `RequestIDMiddleware`：用 `push_request(request_id)` 包裹 `call_next`，使请求内所有日志自动带 rid
- **`app/core/logging.py`**：两个 Formatter 从 `tracing.get_span()` 统一读取 request_id/run_id/node_name
  - ConsoleFormatter 在时间/级别/logger 后追加显示 `run=xxxxxxxx`（前 8 位）与节点名
  - JsonFormatter 新增 `run`、`node` 字段（非空才输出，JSON 契约增量兼容 ELK）
- **`app/main.py`** lifespan：启动日志的 `extra={...}` 并入消息文本（extra 字段不会进 JSON 输出，属顺手修复）

### 2. 异常处理器补日志（`app/core/errors.py`）
- `app_error_handler`：warning（code/status/detail/path）
- `validation_error_handler`：warning（422 字段错误列表）
- `http_exception_handler`：info（404/405 常见，避免噪音）
- `unhandled_exception_handler`：`logger.exception` 替换现在的 `traceback.print_exc()`（errors.py:372）

### 3. Run 调度器（`app/application/workflow_dispatcher.py`）
- `_execute_workflow` 整体包 `with push_run(str(run_id)):` → Worker 全链路日志带 run_id
- 新增 INFO：Run 开始执行（action/project/attempt）、checkpoint 恢复（已完成节点）、Workflow 执行完毕（最终 status/stage_gate/已写集数/总耗时）
- `claim_next`：领取 Run INFO、恢复次数耗尽 WARNING
- `renew_lease` 失败：WARNING（租约可能被接管）

### 4. Workflow 节点统一日志（新建 `app/workflows/node_timing.py`）
- 将 `creation.py:49` 的 `_timed_node` 提取到共享模块并增强：节点开始 INFO、节点完成 INFO（含耗时）、节点异常 WARNING 后原样重抛
- 5 个工作流（revision / evaluation / import_file / outline_revision / conversational_revision）的 `add_node` 全部改用该装饰器——它们现在连 `push_node` 都没有，LLM 埋点与日志均无法定位节点（顺带修复）

### 5. LLM 调用链（黑盒变透明）
- **`app/llm/openai_compatible.py`**：调用开始 INFO（model/schema/prompt_name/max_tokens/timeout）、每次尝试成功 INFO（model/attempt/耗时/prompt+completion tokens/Schema 校验是否通过）、超时与连接失败 WARNING（现有成功路径完全无日志）
- **`app/llm/structured_output.py`**：Schema 校验失败将重试 WARNING（schema 名/attempt/错误摘要）、重试耗尽 ERROR、重试后成功 INFO
- **`app/llm/budget.py`**：软上限跨越 WARNING（calls/n）、硬上限触发 ERROR（抛 BudgetExceededError 前）

### 6. API 路由层（每个功能的核心写操作 1 条 INFO）
- `runs.py`：create（action/options 摘要/user_input 截断 60 字）、cancel、continue（gate/batch/本批终点）、retry
- `agent.py`：对话轮创建（消息截断）、Action 确认/拒绝
- `conversations.py`、`projects.py`、`uploads.py`、`exports.py`、`knowledge.py`、`revisions.py`、`evaluations.py`：创建/确认/上传/导出等写操作
- GET 列表类不加（请求中间件已覆盖，避免噪音）

### 7. Artifact 落库与事件发布
- `app/artifacts/store.py`：保存成功 INFO（type/episode/version/id）
- `app/events/publisher.py`：publish DEBUG（type/run_id，事件频繁用 DEBUG 防噪音）

### 8. 测试与收尾
- 新增单元测试：Formatter 在 `push_run`/`push_node` 上下文正确输出 run/node 字段（放 `tests/unit/observability/`）
- 确认 `tests/security/test_log_scan.py`、`test_log_redaction.py` 仍绿（RedactFilter 行为不变，新日志自动脱敏）
- 跑 `make lint typecheck test`（test 环境 log_level 强制 WARNING，新增 INFO 日志不影响现有测试）
- 按 CLAUDE.md 收尾清单在 `docs/DEV_LOG.md` 追加开发日志条目

## 明确不做
- DB repository CRUD 层日志（噪音大，重要写路径由 store 层覆盖）
- 不引入 structlog/loguru 等新依赖，不加文件 handler（stdout 交给 docker logs）
- rag/tools/memory 内部日志（节点级日志已覆盖外框）

## 日志级别约定
- INFO：功能里程碑（请求受理、Run/节点开始结束、LLM 调用结果、Artifact 落库）
- WARNING：可恢复异常（重试、校验失败、租约丢失、业务 4xx）
- ERROR/EXCEPTION：最终失败（重试耗尽、预算超限、未处理异常）
- 想看更细内容时设 `LOG_LEVEL=DEBUG`（messages 摘要、事件发布）
